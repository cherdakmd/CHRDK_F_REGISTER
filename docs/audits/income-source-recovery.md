# Аудит двойной регистрации источников дохода

## Модель отказа

У финансовых аддонов две durable-записи:

1. Core `bank.json`: `entitlementSources[source] = lineage UUID` и банковские квитанции;
2. локальный JSON модуля: тот же `lineage`, ACK `registered=true`, последовательность и обязательства.

Они не могут быть одной ACID-транзакцией. После восстановления `bank.json` из более
раннего backup Core может не знать lineage, хотя локальный ACK остался. Старый код
видел ACK и только возвращал `false`, не пытаясь восстановить регистрацию. Обратный
разрыв тоже возможен: Core записал lineage, а модуль не успел записать ACK.

Удаление локального JSON создаёт новый UUID и не является восстановлением: при старом
UUID в Core это конфликт. Автоматическая подмена UUID или очистка WAL запрещены.

## Правило безопасного восстановления

Сначала проверить `incomeSourceAvailable(source, lineage)`. Если Core уже знает тот же
UUID, обязательно дозаписать отсутствующий локальный ACK. Если Core не знает источник,
можно повторно зарегистрировать **тот же UUID**, только если локальные данные доказывают
отсутствие любой финансовой истории и незавершённых эффектов. Затем записать ACK.

Другой UUID в Core, неисправное хранилище, банковская последовательность, денежные
обязательства или `pending` при уже записанном `ACK=true` означают fail-closed.
Исключение для Diamond Shop: если локальный JSON был создан заново, а Core сохранил
прежний market, read-only capability проверяет последовательности обеих сторон.
Только при `local sequence=0`, `Core sequence=0` и отсутствии обоих pending локальный
магазин принимает существующий market Core. При банковской сделке или pending adoption
запрещён; новый UUID никогда не заменяет старый в Core.
Первичная регистрация (`ACK=false`) сохраняет прежнее поведение: если модуль смог
зарезервировать обязательство до первого обращения к банку, тот же UUID регистрируется
штатно. Восстановление не начисляет и не списывает деньги, не меняет товары/землю/
прогресс, не закрывает WAL.

## Проверенные модули

| Источник | Условия автоматического восстановления при потере lineage |
|---|---|
| `diamond-shop` | `sequence == 0`, `pending == null`, хранилище исправно |
| `claim-land` | `financialSequence == 0`, `financialPending == null`, хранилище исправно |
| `daily-rewards` | все cumulative totals равны нулю, нет frozen rewards |
| `teleports`, `guilds`, другие `PaidActions` | journal sequence 0, нет pending/actions/refunds/resolutions |
| `common-goals` | charge sequence 0, нет pending, `lifetimeEarned == 0`, entitlements пусты |
| Milestones (`skills-awards` и др.) | cumulative totals пусты; нулевые legacy-claimed допустимы |
| `orders-income` | нет предметного pending и cumulative incomes |
| `battlepass-rewards` | **не восстанавливается по ACK=true**: witness не доказывает отсутствие прошлых выплат |

Для `PaidActions` также исправлен порядок проверок: рассинхрон sequence при отсутствии
истории больше не включает `paused` до попытки восстановления. При любой реальной
истории прежняя fail-closed проверка сохраняется.

## Что намеренно не автоматизировано

- восстановление источника с прошлыми сделками или выплатами по более раннему bank.json;
- замена lineage на новый/чужой UUID;
- ручной сброс `pending`, sequence, refunds, incomes или entitlement receipts;
- повторная выдача наград Battle Pass при неизвестном банковском прошлом.

Такие случаи требуют согласованной пары backup модуля и Core либо отдельного аудита
квитанций. Нельзя удалять JSON, чтобы «разблокировать» сервис.

## Проверки

Регрессии используют настоящий `BankStore` и локальные durable stores: восстановление
того же UUID до первой операции, дозапись ACK, запрет другого UUID и запрет после
сделки/награды/pending. Денежные суммы при регистрации не создаются.
