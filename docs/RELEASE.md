# Подготовка и публикация стабильного релиза

Документ описывает выпуск плагинов CHRDK. Публикация исходников, установка на
Minecraft-сервер и публикация товаров TradeMC — три отдельных действия.

## 1. Подготовить ветку

1. Убедиться, что рабочая копия чиста, а основной `Build` зелёный.
2. Обновить `plugin_version` в `gradle.properties` (например, `1.5.2`).
3. Добавить `docs/releases/<версия>.md`, актуальный блок в начало
   `docs/releases/update-memo.txt` и краткие заметки в `README.md`.
4. Не менять `Core API`, цены, схемы хранения и состав модулей неявно. Такие
   изменения должны быть явно описаны вместе с миграцией и порядком отката.
5. Для RC использовать только суффикс `-rc.N`, где `N >= 1`. RC публикуется
   исключительно как GitHub prerelease.

Локальная проверка при установленной Java 25:

```bash
python3 .github/scripts/check_retired_addons.py
python3 .github/scripts/check_messages.py
python3 -m unittest discover -s .github/scripts -p 'test_*.py' -v
python3 .github/scripts/gradle_build.py
```

Полный обязательный набор дополнительно включает проверки TradeMC, wiki,
clan_shop, datapacks и offline social из `.github/workflows/build.yml`.

## 2. Собрать dry-run комплект

После merge кандидата в `main` запустить **Release → Run workflow**, указав в
`version` точное значение из `gradle.properties`. Например:

```bash
gh workflow run release.yml --ref main -f version=1.5.2
```

Ручной запуск выполняет тот же Gradle build, тесты, проверку 22 общих JAR,
отдельных `CHRDK_VK`/`CHRDK_Disasters`, Mine Treasure, ZIP CRC и версий, но
**не создает тег, Release и не загружает публичные ассеты**. Результат сохраняется как временный artifact
`release-candidate-<версия>-<sha>`.

Скачать candidate и проверить контрольные суммы:

```bash
sha256sum -c chrdk-1.5.2-SHA256SUMS.txt
unzip -t chrdk-plugins-1.5.2.zip
```

Архив должен содержать ровно 19 JAR одной версии и `ОБНОВЛЕНИЕ.txt`.
`chrdk-vk-<версия>.jar`, `chrdk-disasters-<версия>.jar` и
`mine-treasure-1.6.5-ru.zip` остаются отдельными файлами.

## 3. Провести обязательный staging gate

До стабильного Release на отдельной копии production:

- сделать согласованный backup миров, playerdata, всех `plugins/CHRDK_*`,
  финансовых JSON/WAL и конфигураций;
- остановить сервер штатно, заменить весь комплект без `/reload` и без старых
  дублей JAR; `CHRDK_VK` установить отдельно;
- проверить запуск, включение всех плагинов, регистрацию/вход/2FA, команды и
  GUI изменённых модулей, PlaceholderAPI, LuckPerms и отсутствие ошибок;
- проверить миграции, повторный запуск, восстановление после restart и
  критичные финансовые операции с идемпотентностью;
- проверить внешние интеграции, затронутые выпуском (VK/MAX, TradeMC, RCON);
- записать результат и нерешённые ограничения в заметки релиза.

Зелёный CI и dry-run не заменяют живой smoke/нагрузочный тест.

## 4. Опубликовать

1. Создать tag `v<версия>` на том же коммите, который прошёл dry-run.
2. Сначала создать **draft** Release с заметками и известными ограничениями.
3. Для RC отметить prerelease; для стабильной версии снять этот флаг.
4. Опубликовать Release. Workflow ещё раз соберёт tagged source и прикрепит:
   - `chrdk-plugins-<версия>.zip`;
   - `chrdk-vk-<версия>.jar`;
   - `chrdk-disasters-<версия>.jar`;
   - `mine-treasure-1.6.5-ru.zip`;
   - `chrdk-<версия>-SHA256SUMS.txt`.
5. Дождаться успешного Release workflow и сверить размер/число ассетов,
   контрольные суммы и ZIP. Не переписывать опубликованный стабильный тег.

Если сборка после публикации упала, Release нельзя считать готовым: перевести
его обратно в draft или явно пометить непригодным, исправить причину и выпустить
новый тег. Не подменять ассеты вслепую.

## 5. После публикации

Установка на production выполняется только по отдельному решению, после backup
и с планом отката. Старые данные и финансовые журналы не удалять. Проверить
фактические версии через `/plugins`, журналы запуска и основной пользовательский
сценарий. Публикация VK/TradeMC также требует отдельного подтверждения.
