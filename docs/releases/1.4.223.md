# 1.4.223 — безопасный депозит и аукцион на общем /bal

## Для игроков

- `/bal deposit all`, `hand` и числовая сумма сначала строят точный план 36
  storage-слотов и проверяют предел банка. Отказ не снимает предметы, не разменивает
  блоки в алмазы и не выбрасывает возврат на землю. `hand` — выбранный слот основной
  руки, не offhand; числовой депозит по-прежнему принимает только обычные алмазы.
  Именные/зачарованные предметы и остальные слоты сохраняются.
- Аукцион оплачивается **сначала с личного `/bal`**. Недостача — обычными алмазами,
  алмазной/глубинной рудой (1) и алмазными блоками (9) из storage. Мелкие номиналы
  расходуются первыми; сдача от блока поступает в банк. Именные предметы, PDC,
  offhand, броня и курсор не используются. Нестандартные стаки не расходуются.
- Если счёт покрывает цену, инвентарь покупателя **вообще не устанавливается заново**
  и `saveData()` для оплаты не вызывается. Товар остаётся в `/ah mail` до получения.
- Выручка за вычетом прежней комиссии сразу приходит в общий `/bal`, в том числе
  офлайн-продавцу. `/ah money` и кнопка меню теперь показывают этот же счёт:
  повторной выдачи старых денег предметами нет. Снять алмазы можно через `/bal withdraw`.
- Цены, комиссия с округлением вверх, сроки, лимиты лотов, подтверждение, права,
  почта, снятие и бесплатное истечение сохранены. Survival и Adventure разрешены;
  Creative/Spectator, NPC и неавторизованный плательщик не допускаются.
- Если достигнут предел счёта продавца/покупателя или банк не работает, сделка не
  заменяется физической выдачей: лот/источник выручки сохраняются, торговля приостанавливается.

## Старые данные

Сначала завершается старый `schema=1` WAL по прежним снимкам, включая `BUY` и
`WITHDRAW`. Только после этого рынок записывается в `schema=2` с постоянным UUID
и монотонным финансовым счётчиком. Старый `state.money` остаётся **неизменяемым
источником миграции**, а не дополнительным расходуемым балансом.

Каждый UUID получает once-import в `bank.json`: сумма и квитанция записываются
вместе синхронно. Повтор после перезапуска или после расходования `/bal` не начисляет
деньги снова. Для офлайн-владельцев запускается очередь по одной записи за тик;
покупатель и продавец проверяются непосредственно перед своей сделкой. Нехватка
места на банковском счёте не обнуляет источник: повтор возможен при входе владельца
или покупке его лота. Изменённая сумма источника/другая идентичность рынка вызывает
остановку, а не повторное зачисление. Не удаляйте и не «чистите» старый `money` вручную.

## Протокол оплаты и восстановление

API **15** добавляет immutable `AuctionPayment`, общий целочисленный `AuctionTender`,
проверку доступности, once-import и запрос авторитетного статуса платежа. Старое ядро
или неизвестный поставщик API не включают финансовый fallback.

1. Аукцион сохраняет pending: намерение с UUID, рынок, следующий счётчик, лот,
   стороны, цену/комиссию, банковскую и предметную части, сдачу и SHA-256 двух снимков.
   `pending.next` переносит лот в почту покупателя, но **не** в старый `money`.
2. Ядро повторно проверяет плательщика, права, режим, ожидаемые storage-слоты,
   bank-first план, номиналы, суммы и хеш. Дебет, выручка, сдача и квитанция пишутся
   **одним `bank.json` до изменения предметов**.
3. Только подтверждённая квитанция разрешает применить предметную часть, сохранить
   playerdata и опубликовать `pending.next`. При нулевой предметной части эти действия
   с инвентарём пропускаются.

Статусы: `COMMITTED`, `MISSING`, `CONFLICT`, `UNAVAILABLE`. Отрицательный результат
записи не означает «оплаты не было»: после неоднозначного IO банк останавливается
до проверки/перезапуска, pending сохраняется. Нельзя автоматически возвращать деньги.

- **Только банк:** `COMMITTED` завершает почту, `MISSING` отменяет pending. Это возможно
  на старте без входа владельца и без проверки его актуального инвентаря. Равные
  before/after допустимы только у проверяемого банковского намерения без наличной части.
- **Есть предметная часть:** после авторизации владельца `COMMITTED + before` применяет
  after; `COMMITTED + after` сохраняет/завершает. `MISSING + before` отменяет pending.
  `MISSING + after`, посторонний снимок, конфликт или неизвестный статус не дают
  угадать исход: журнал остаётся, владелец предметной операции отключается до проверки.
- Старые `LIST`/`ITEM` продолжают восстанавливаться по двум разным снимкам. Изменение
  схемы, удаление квитанции, счётчика или финансовых таблиц не превращает банковский WAL
  в старый inventory-only протокол.

Банк хранит последнюю полную квитанцию и high-water **на рынок**, а не бесконечный
список покупок. Идентичный повтор последнего платежа — no-op; старые, пропущенные и
конфликтующие последовательности запрещены. В рынке может быть только один pending.
Квитанции импорта хранятся на UUID источника. Отсутствие импортов участников не
считается доказательством неоплаты: потерянный файл банка нельзя принять за `MISSING`.

## Эксплуатация и границы гарантий

- Банк теперь пишет schema 2; schema 1 читается для обновления. Новые таблицы
  сохраняются также обычным async-сохранением и JSON-снимком. Синхронизированный
  писатель не позволяет устаревшему async-снимку затереть новую квитанцию.
- Финансовая запись: временный файл, `force(true)`, atomic replace и синхронизация
  каталога. Файловая система должна поддерживать эти операции; небезопасного fallback
  к неатомарной замене нет. Ошибка записи блокирует дальнейшие финансовые изменения.
  Ошибка аукциона также блокирует его ledger до перезапуска.
- `/ahadmin status` показывает pending; `/ahadmin recover` умеет проверить банковскую
  покупку без онлайн-владельца. Для предметной операции нужен авторизованный владелец.
  При ошибке IO сначала проверьте диск/права и сделайте копии, затем перезапустите.
- Это согласованный WAL/receipt-протокол, **не распределённая ACID-транзакция** между
  двумя JSON и Minecraft playerdata. Для восстановления из резервной копии нужны
  согласованные `CHRDK_Core/bank.json`, `CHRDK_Auction/market.json` и playerdata одного
  остановленного сервера. Независимый откат одного файла — конфликт, не повод для
  автоматического возврата. Не удаляйте pending, счётчики или receipt-таблицы.
- Обычный депозит сохраняет прежнее async-сохранение банка и не объявляется crash-atomic
  с playerdata. Изменён именно безопасный отказ/снятие предметов; механизм снятия
  `/bal withdraw`, Lottery, CommonGoals, Guild и Teleports в эту миграцию не входят.

## Проверки

Добавлены тесты реального `BankStore`, `AuctionStore`, общего планировщика и чистой
recovery state machine: once-import/повтор/перезапуск, сохранение Shop/Claims receipts,
банк/предметы/смешанный платёж, сдача/пределы, high-water и старые WAL, равные снимки,
сбой временного файла, quarantine, повреждённые поля и порядок production-вызовов.
Тесты без Paper-сервера не заменяют live crash/inventory smoke-test: перед установкой
проверьте эти сценарии на копии данных с целевым Purpur.

Версия всех модулей — **1.4.223**, API — **15**. Tag, GitHub Release и установка на
сервер не выполняются без отдельной команды. Материалы TradeMC не обновляются.
