# 1.4.235 — DiamondShop: сохранённая сделка от предметов до рынка

**Этап общего аудита, без отдельного релиза и установки. Core API 23.**
Закрывает прежний путь `exchangeDiamonds → отдельно stock/оборот` в магазине.
Claims земля/аренда и конфигурационные денежные выходы DailyRewards/Treasures
остаются блокирующими пунктами общего релиза.

## Правила торговли сохранены

Цены/spread, целые партии, GUI-котировки, лимиты, календарные сутки UTC и права
не менялись. Новая сделка требует авторизованного живого игрока без NPC, Survival,
`chrdkshop.use`, исправного включённого банка и согласованных native-квитанций.
Основной источник — `/bal`, обычные физические средства покрывают только недостачу;
целая сдача и выручка идут в банк. Курсы из пользовательского конфига замораживаются,
включая пользовательские положительные целые курсы/материалы. Неизвестные Material
не добавляют покупательной силы и не попадают в native-план. Предметы с meta,
вторая рука, броня и курсор не используются. Денежных drops и частичной выдачи нет.

## Пять подтверждаемых шагов

1. В `shop-data.json` сохраняется заявка: UUID рынка/операции/владельца, монотонная
   sequence, направление, товар, штуки, целая цена, debit/credit/physical, курсы,
   точные BEFORE/AFTER storage. Вместе с ней заморожен эффект рынка: запас,
   счётчики покупки/продажи, оборот, принятое UTC-окно и точка истории/её настройки.
2. Core проверяет source binding, последовательность, текущий BEFORE, обычность
   затронутых предметов и **реконструирует весь native-план**. В canonical
   `bank.json` v6 фиксируется SHOP-intent и резерв владельца, без изменения баланса.
3. Storage и PDC `chrdk_core:cash_transfer` сохраняются как playerdata. AFTER без
   nonce не считается доказательством. Свой nonce после ошибки saveData требует
   успешного checkpoint текущего playerdata, не повторного grant/consume.
4. Одним replace bank.json меняются баланс, gross-счётчики debit/credit,
   последняя cash-квитанция, market-квитанция и удаляется owner pending.
5. Только по COMMITTED Core receipt один replace shop-data.json применяет весь
   frozen stock/статистику/историю/UTC-оборот, повышает sequence и удаляет заявку.
   Сообщение об успехе идёт после полного подтверждения этих шагов.

Оба writer используют snapshot+file force+atomic replace+directory force под
монитором; неопределённость IO/runtime останавливает writer. После rename новый
финансовый результат не затирается старым RAM-снимком при выключении.

На время source pending **рынок целиком зарезервирован**: нельзя принять другую
сделку, изменить запас админ-командой, передвинуть stock recovery или квоту/историю.
Это сознательный выбор последовательного рынка вместо некорректного параллельного
учёта динамической цены. В Core резервируется только счёт владельца: переводы,
оплаты и новые доходы этого UUID ждут; остальные банковские счета работают.

## Повтор и recovery

- Recovery запускается при авторизации и ограниченной задачей main thread
  (один market pending, проверка раз в секунду). PREPARED требует владельца,
  его авторизации и native proof; COMMITTED закрывает рынок даже без онлайн-игрока.
- Уже принятый durable source intent не переоценивается по новому курсу/цене,
  каталогу, лимиту, режиму или правам. Авторизация и реальное native-доказательство
  остаются обязательными. Новые заявки проходят текущие проверки Core/магазина.
- Последняя market-квитанция хранится отдельно от latest owner cash marker:
  новая банковская операция владельца не уничтожает доказательство старой сделки.
  Старый AFTER никогда не подставляется вместо законно изменившегося инвентаря.
- После полуночи записывается **принятое UTC-окно**, а не день восстановления.
  Следующий дневной лимит не расходуется повторным закрытием старой заявки.
- Невозможный/переполненный счётчик или потеря точности при сложении денежного
  оборота отклоняются до Core-intake, а не после списания денег.
- UNAVAILABLE не означает MISSING. Исчезновение принятого Core-intent или конфликт
  transaction/sequence/market блокируют источник до сверки. Нет guessed refunds.
- Если здоровый Core **после отказа intake** авторитетно подтверждает MISSING,
  неподтверждённая заявка может быть удалена без изменения sequence/рынка/предметов/
  денег. Это отмена ещё не принятого Core запроса (например, изменившегося BEFORE
  или нехватки headroom), не откат оплаченной сделки. Неизвестный банковский исход
  никогда не разрешает эту отмену; ранее PREPARED не отменяется так.

## Форматы и перенос

`shop-data.json` получает schema 1, market UUID, sequence и необязательный pending.
Старый формат без этих полей читается без создания сделок/денег. UUID рынка сначала
становится durable, потом привязывается к Core `diamond-shop`. Потеря source-файла
или независимый reset lineage не создают новый бесконтрольный рынок.

Bank schema 1–5 поддерживаются; следующая запись — v6 с обязательным
`shopSettlements`. Новые поля нельзя спрятать понижением schema. Старые cash
intents/receipts, прочие финансовые receipts и коллективные источники сохраняются.
Оба файла строго проверяют типы новых полей, UUID, связи sequence и frozen effect.

Старый импорт магазина теперь также force+atomic до успешного ACK. Квитанция
проверяется до повторного расчёта старого остатка: уже выполненный импорт не
начисляется заново и не блокируется из-за обнаруженного точного дробного хвоста.
Новые импорты сохраняют BigDecimal→CEILING и cap; неизвестный UUID без банковского
профиля/авторизованного игрока/локального native-профиля не импортируется наугад.

DiamondShop требует Core API 23+ и отказывает при старом ядре. Публичные методы
API 23 — доверенный серверный протокол магазина, **не команда произвольной выдачи**:
модуль обязан сначала durably сохранить проверенный source intent.

`/shopadmin recovery` — read-only диагностика (штатное `chrdkshop.admin`): исправность,
market, sequence, pending transaction/owner и банковский статус. Она не удаляет WAL,
не меняет баланс и не выдаёт предметы. Reload не снимает финансовый карантин.

## Проверки и границы

47 новых тестов: 23 `ShopNativeBankTest` с настоящим BankStore и production
InventoryTransfer/BankCash, 24 `ShopJournalTest` с настоящим ShopStore/NIO и
production source-recovery. Фиктивны native playerdata-порт и банковский bridge
в source-тестах; это не live crash-test Minecraft и не обещание распределённого ACID.

Матрица: оба направления, bank-first/change, zero-bank-delta physical buy,
резерв/cap/достаточность, фальшивый AFTER, неопределённый saveData/current checkpoint,
IO до/после rename в prepare/finish обоих файлов, runtime, повтор/restart/spend,
новая cash-квитанция поверх market receipt, sequence/lineage/reset, два владельца,
legacy import ACK, schema5→6, frozen config/UTC, защита admin/истории/квоты,
отсутствие callback/drop path и read-only диагностика. Старые source-contract и
миграционные fixtures обновлены под новые схемы, прежние проверки сохранены.

Локально: сообщения всех модулей, diff, 22 теста прежней витрины и 11 тестов
release-validator. Версия обновлена в существующей текстовой метаинформации,
без новых карточек/изображений/архивов. Общая сборка — Root + 29 модулей,
Java 25/Purpur 26.3 в GitHub Actions.

**Согласованные резервные копии bank.json, shop-data.json, playerdata и мира на
остановленном сервере обязательны.** Nonce не является независимым доказательством
истории всех файлов. Не удалять pending и не откатывать один финансовый файл для
«починки» сделки. Повреждённые/несогласованные источники требуют сверки, не угадывания.
