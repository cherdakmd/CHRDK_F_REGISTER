## Production-отказ 2.0.3 и корневая причина

На продакшене (Purpur 26.3-2658, Java 25.0.2, полный комплект 2.0.3) CHRDK_Claims
отключался при каждом старте: `/claim` и `/claimadmin` отвечали «Cannot execute
command … plugin is disabled». Причина установлена по логу запуска:

1. При старте `PaidActions` видел, что банк уже зарегистрировал источник
   `claim-teleports` со своим lineage, и усыновлял его: `paid-actions.json`
   переписывался («Источник claim-teleports: принят lineage банка; финансовых
   обязательств не было, значения сохранены»).
2. Файл журнала `bank-charge.json` при этом оставался со старым lineage —
   adopt-путь его не переписывал.
3. Сразу после этого повторное открытие `ChargeJournal` сверяло lineage и падало
   (`journal lineage` → «Повреждён bank-charge.json; не удаляйте журнал»),
   `ClaimsPlugin.onEnable` отключал плагин.

Любой adopt-случай был обречён, включая первый старт со свежим журналом:
отказ повторялся на каждом старте. Прод-данные не повреждены — «данные не
сброшены», обязательства и балансы на месте; расхождение касалось только
идентичности двух файлов одного журнала.

## Что исправлено

- `PaidActions.reconcileLineage` переопознаёт `paid-actions.json` и
  `bank-charge.json` **вместе** на зарегистрированный lineage банка — строго пока
  в журнале нет ни одного финансового обязательства (`pending` нет, sequence 0,
  actions/refunds/resolutions пусты).
- Fail-closed сохранён: любые финансовые обязательства, повреждённый файл или
  неизвестный lineage банка — прежняя остановка модуля без изменения файлов.
- Регресс-тесты `ChargeLineageAdoptTest`: adopt обоих файлов, лечение прерванного
  adopt (фактическое состояние продакшена), отказ при pending/обязательствах/
  повреждении файла и порядок reconcile до открытия журнала.
- Поведение валидации намерения `ChargeJournal` сохранено без изменений
  (невалидный план не карантинирует журнал).

## Установка и первый запуск

1. Остановить сервер штатно и сохранить согласованные backup миров, playerdata,
   всех `plugins/CHRDK_*`, финансовых JSON/WAL и конфигураций.
2. Проверить manifest, SHA-256 и состав комплекта: 19 основных JAR версии
   2.0.3-fix, `chrdk-vk-2.0.3-fix.jar` и `chrdk-disasters-2.0.3-fix.jar`
   отдельными файлами. Mine Treasure — тот же `mine-treasure-1.6.5-ru.zip`,
   замена не требуется. Не смешивать версии комплекта.
3. На остановленном сервере заменить весь комплект одновременно, без `/reload`,
   PlugMan, старых дублей JAR и удаления данных.
4. Первый запуск идёт с теми же мирами, playerdata и финансовыми файлами.
   Расхождение lineage лечится автоматически: оба файла журнала согласуются на
   lineage банка, значения сохраняются. **Не удалять и не править вручную**
   `bank-charge.json`, `paid-actions.json`, `bank.json`, WAL и playerdata.
5. Сохранить полный startup log: строки «Источник claim-teleports: принят lineage
   банка» (если adopt был нужен) и отсутствие «Повреждён bank-charge.json».
   Убедиться, что Claims включён, `/claimadmin recovery` отвечает, а `/claim`
   работает.
6. Проверить обычную Claims-операцию и restart: сверить исходный/конечный баланс,
   сохранность pending и отсутствие повторного списания. Unknown outcome
   оставлять закрытым для ручной сверки; никаких повторных списаний/зачислений.

Откат — по полному backup; финансовые файлы восстанавливать согласованно с Core.
Вайп/сброс для этой версии не нужны.

## Известные ограничения

- Staging-сценарии Claims committed / definitively-missing / unknown на живой
  копии не пройдены (как и для 2.0.3) — Claims нельзя считать полностью
  проверенным до отдельного staging-отчёта. При неизвестном финансовом исходе
  операция остаётся закрытой и не повторяется автоматически.
- Фикс устраняет именно воспроизведённый production-отказ; он не отменяет общие
  правила: неизвестный исход не считается отменой, обязательства не удаляются,
  данные не сбрасываются.
