## Инцидент 1: карантин /shop «Не совпадает frozen effect рынка»

При каждой покупке через «Кузню» рынок уходил в карантин, зависший pending
встречал владельца при каждом входе (onAuthenticated → recoverPending →
повторный stop). Корневая причина — разные единицы измерения заморозки:

1. `prepareForge` замораживала `round(turnover + trade.money())`, то есть
   **сотые** алмаза, а `Pending.matches` ожидала `round(turnover +
   turnoverWhole)`, то есть **целые** алмазы.
2. Реальный pending продакшена: покупка 8 ECHO_SHARD (sku `ascend`,
   `rateBps=9250`), `money=944` (9,44 ⛁) при базовом обороте 778.0 —
   заморозка **1722.0 = round(778 + 944)** против ожидаемых
   **788.0 = round(778 + turnoverWhole(10))**; владелец — kalinin_play,
   22:37:33.978 МСК — за секунду до ERROR в логе.

Что исправлено:

- `ShopStore.prepareForge` замораживает эффект через `t.turnoverWhole()`;
- `ShopJournal.frozenEffect(frozen, old, money, turnoverWhole)` принимает
  **обе** формулы — legacy-заморозка распознаётся и не карантинит рынок;
- `ShopStore.finish` лечит legacy-forge-pending: пересоздаёт Pending с истинным
  эффектом (переписывает счётчики ×100 на целые алмазы).

**Зависший pending продакшена довершится сам при первом старте** этой сборки:
сделка засчитается, `turnover` станет 788.0, последовательность — 78. Файл
`shop-data.json` руками не править и не удалять. Реальные числа инцидента
закреплены регресс-тестом
`ForgeFreezeContractTest.productionPendingFromIncidentIsAcceptedAndHealed`
(PR #99).

## Инцидент 2: забор предмета из наковальни молча не срабатывал

После операции ASCEND `refreshTierModifiers` терял базовые характеристики,
`ItemAttributeMergeListener` возвращал их в `result` — итоговый стек отличался
от показанного превью, и `current()` молча гасил клики (в логе продакшена —
тишина). Исправлено:

- `ForgeAnvilListener` на MONITOR `merged(PrepareAnvilEvent)` догоняет display
  за объединённым стеком результата;
- забор предмета выдаёт `ForgeAnvilPreview.give(display, previewLines)` — то,
  что игрок видел в превью;
- чистая логика вынесена в `ForgeAnvilPreview` (stale/strip/give) и покрыта
  тестами `ForgeAnvilPreviewTest`, `ForgeAnvilTakeContractTest`.

## Диагностика витрины /shop (PR #100)

- строка `CHRDK_DiamondShop включён: товаров N (разделы: …, books-custom=76,
  books-vanilla=42, …)` показывает, что реально попало в каталог;
- если список книг непуст, а в каталог не попала ни одна книга, — сводное
  предупреждение с именем пропавшего раздела вместо тишины.

Поведение витрины и сделок не менялось.

## Установка и первый запуск

1. Полный комплект: 19 JAR одной версии из `chrdk-plugins-2.0.5.zip`;
   `chrdk-vk-2.0.5.jar` и `chrdk-disasters-2.0.5.jar` — отдельно;
   `mine-treasure-1.6.5-ru.zip` **не заменять**.
2. Согласованный backup миров, playerdata, `plugins/CHRDK_*`, финансовых
   JSON/WAL и конфигураций; остановить сервер штатно; заменить комплект без
   `/reload` и без старых дублей JAR.
3. **Не удалять** `shop-data.json`, `bank.json`, `bank-charge.json`,
   `paid-actions.json`, `claims-data.json`, `welcome-gifts.json` и playerdata.
4. После запуска: `/pass doctor`, `/shopadmin recovery`, `/shop` (покупка через
   «Кузню» двумя игроками), наковальня (ASCEND → забор предмета), проверка
   `/shop price` и `/bal`. Стартовая строка магазина должна показать
   `books-custom=76, books-vanilla=42`.
5. Вайп не требуется; неизвестный исход не разрешается автоматически — при
   аномалиях остановиться и сохранить логи.

Область комплекта зафиксирована в [2.0.5.json](2.0.5.json).
