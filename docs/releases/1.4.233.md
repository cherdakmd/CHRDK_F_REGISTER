# 1.4.233 — журналируемый депозит и снятие банка

**Этап общего аудита, не отдельный релиз. Core API 22 без повышения.**
Публикации/установки нет. Следующие блокирующие пути: DiamondShop, земельные
платежи/аренда Claims, денежные награды DailyRewards и обычные алмазы Treasures loot.

## Для игроков

- `/bal deposit [all|hand|сумма]` и `/bal withdraw <сумма>` больше не связывают
  банк с инвентарём обычным callback без долговечного подтверждения.
- Снятие выдаёт точный план в 36 storage-слотов. Нет `addItem` с возможным остатком
  и страховочного выброса алмазов на землю. Если целая сумма не помещается,
  ни инвентарь, ни баланс не меняются.
- Депозит сохраняет правила: только обычные DIAMOND/DIAMOND_BLOCK, курс блока
  из `economy.block-worth`; числовой депозит принимает только обычные алмазы,
  без размена блока. Руды, именованные/component-предметы, offhand, броня и курсор
  не участвуют. `hand` означает выбранный storage-слот основной руки.
- До принятия проверяются предел счёта/достаточность баланса/вместимость.
  Проверка прежних `charge_*`-квитанций не позволяет разменять предметы уже
  принятой оплаты аддона, если её native-checkpoint ещё не подтверждён.
  Новые предметные обмены требуют авторизации, `chrdkregister.bal`, без NPC,
  Survival/Adventure. В Creative/Spectator денежный выход закрыт.
- При незавершённом обмене резервируется **только счёт владельца**, а не весь банк.
  Оплаты, переводы в обе стороны, импорты, прямые изменения и новые доходы этого
  счёта ждут восстановления. Источники наград не теряют свою задолженность;
  остальные игроки могут продолжать пользоваться банком.

## Canonical bank.json v5

Два новых обязательных раздела: `cashPending` (один intent на UUID) и
`cashReceipts` (последний завершённый обмен с последовательностью и nonce).
Исторические balance/receipts/источники прочих модулей сохраняются.
Схемы 1–4 читаются без ретровыдачи, автоматического обмена inventory и создания
исторических cash-receipts. Следующая запись использует v5. Понижение schema
при оставленных новых финансовых таблицах запрещено.

Протокол:

1. Проверенный план фиксирует UUID, transaction, sequence, направление, сумму,
   баланс BEFORE, курс/режим депозита и оба точных storage-снимка.
2. Intent и резерв владельца синхронно записываются в `bank.json` до native-вызова.
   Сам баланс пока не меняется и не может быть потрачен параллельным путём.
3. Native storage и PDC `chrdk_core:cash_transfer` сохраняются одним playerdata.
4. Только после подтверждения одним bank.json replace меняются баланс,
   lifetime-счётчики, latest-receipt и удаляется pending.

Это один банковский source, а не второй расходуемый кошелёк или отдельный
несогласованный журнал снятий. Автосохранение и финансовые replace используют
один монитор; старый async-снимок не затирает резерв или новую квитанцию.
Запись — file force → atomic replace → directory force, dirty снимается после ACK.

## Recovery и отказ

- Авторизация и ограниченная проверка онлайн-игроков (до 16 в секунду) восстанавливают
  сохранённое намерение. Для уже принятой операции новый конфиг курса, режим игры
  и изменившиеся права не переоценивают замороженный план; авторизация обязательна.
- BEFORE с правильной предыдущей отметкой допускает завершение сохранённого запроса.
  AFTER без текущего nonce не считается успешным consume/grant.
- Свой nonce требует checkpoint **текущего** playerdata: saveData мог раньше бросить
  исключение и оставить отметку только в памяти. Повтор не выдаёт/не списывает вещи
  заново и не заменяет законно изменившийся inventory старым AFTER.
- Команда, застигшая старый pending, сначала восстанавливает его, но не создаёт
  ещё один обмен тем же вызовом. После auth recovery новый явный запрос — новая операция.
- После закрытия WAL latest-receipt продолжает проверять PDC. Потерянная отметка
  playerdata, чужой nonce или orphan отметка после потери bank.json блокируют игрока
  до сверки, без автоматического возврата или создания нового доказательства.
- IO/runtime-сбой до rename оставляет прежний intent/баланс, после rename — вместе
  новую квитанцию и баланс. Неизвестный исход останавливает банковский writer;
  shutdown не перезаписывает его старым in-memory состоянием.
- Структура новых таблиц, UUID, поля, целочисленные типы/границы и последовательности
  проверяются строго. Duplicate JSON-поля, неверный синтаксис и trailing garbage
  не принимаются. Native-план дополнительно проверяется до исполнения; повреждение
  останавливает банк без перезаписи оригинала. Файл ограничен 64 MiB.

`/bal recovery` — только диагностика с `chrdkregister.admin`, в том числе когда
банк недоступен. Показывает исправность и количество intents/receipts, не отменяет
операции, не сбрасывает квитанции и не выдаёт деньги. Автоматических финансовых
уведомлений на каждый вход не добавлено; сообщения об успехе идут после полного ACK.

## Проверки

31 новый `BankCashTest`: настоящий BankStore и production recovery executor,
фиктивен только native playerdata. Проверяются оба направления, intent/receipt,
spend/restart/retry, последовательности, cap/достаточность/место, AFTER без nonce,
неопределённый saveData/checkpoint, IO до/после rename при prepare/finish, runtime,
резерв владельца против всех прежних платёжных путей, изоляция двух владельцев,
задержанные доходы, auction parties, legacy v4, повреждённые метаданные/downgrade,
dirty ACK и гонка async writer. Контракты проверяют отсутствие money drops/старого
callback, auth recovery, main-thread storage-only план и admin-gate диагностики.
Старый deposit call-site тест обновлён под журналируемый протокол.

Локально: сообщения всех модулей, diff, 22 теста существующей витрины и 11 тестов
release-validator. Версия обновлена только в прежней текстовой метаинформации
витрины, без новых карточек/изображений/ZIP. Полная сборка: Root + 29 аддонов,
GitHub Actions Java 25/Purpur 26.3. Это не live crash-test Minecraft.

Независимые bank.json/playerdata/мир не являются распределённой ACID-системой.
Отметка playerdata не заменяет согласованные резервные копии всех финансовых
source/journal-файлов и мира на остановленном сервере. Не удалять pending и не
понижать версию банка для ручного «исправления» неопределённой операции.
