# 1.4.282 — отображение оформления клана (кандидат RC.6)

Подготовлено исправление; стабильный релиз, установка на Minecraft-сервер и публикация TradeMC не выполнялись.

- Анимации aurora / shine / pulse передают готовые RGB-цвета символов. Кадр сохраняется после шаблона клана, сериализации, выделения метки в Core и финального рендера чата/TAB; односимвольный тег тоже меняет цвет.
- В TAB один общий таймер обновляет только имена с действующей анимацией. Теперь можно отключить общее периодическое обновление шапки (`tablist.refresh-ticks: 0`), не останавливая анимацию. Пустой/изменённый формат больше не гасит активную анимацию; явное tablist.enabled=false остаётся административным выключателем.
- В чат попадает кадр на момент отправки; история не переписывается. Красная/зелёная статусная рамка клана сохраняется, цвет эффекта остаётся внутри тега, ник/соседние метки не перекрашиваются.
- По отдельной команде владельца отменены ожидание переноса 24 часа, предложения участников и согласования. Менять, применять и снимать все четыре типа оформления может только текущий глава по своим действующим личным лицензиям. Покупки, цены и сроки сохранены.
- Участникам доступен предпросмотр без применения. Команды, клики и отложенные клики повторно проверяют роль; `clear` совместим с `off` и не стирает выбор других покупателей. Старые сохранённые варианты участников не подменяют выбор главы.
- При смене главы/выходе владельца из клана/истечении лицензии старый эффект выключается. Лицензии не удаляются и не передаются новому главе. Старый `clan-styles.json` schema 1 читается без удаления и без ожидания по movedAt.
- GUI и `/clan style status` показывают активную анимацию текущего клана. Stock-тексты об ожидании и согласованиях мигрируют только при точном совпадении; авторские тексты не перезаписываются. Текстовые материалы магазина обновлены без изменения утверждённых PNG и без публикации TradeMC.

## Проверка после отдельного разрешения на установку

1. Главе с действующим «Клановым комплектом» выбрать `/clan style animation aurora` (либо shine / pulse). Переключать все варианты и переносить в свой текущий клан можно сразу.
2. Проверить отказ участнику и офицеру через команды и старый открытый GUI. Сменить главу до отложенного клика: старый глава не должен применить оформление.
3. В TAB наблюдать смену RGB внутри статусной рамки. Отправить новые сообщения в разные моменты: кадры новых сообщений различаются, история неизменна. Проверить `refresh-ticks: 0`, затем восстановить настройку.
4. Проверить снятие/истечение лицензии и смену главы. Лицензии участников не списываются и не передаются. Старые выборы участников не включаются вместо выбора главы.
5. Перезапустить с существующим schema 1 clan-styles.json: данные сохранены, ограничение по старому movedAt отсутствует. Сделать backup Core и Guilds до установки.

Автотесты проверяют фактические цвета в полном пути клан → Core → чат/TAB для всех эффектов/шаблонов/коротких и экранированных тегов, неизменность старого сообщения, роль главы при смене руководства, мгновенный перенос/перезапуск и неизменность чужих покупок.

## RC.5: дополнительный аудит жизненного цикла TAB

По выбору владельца продолжается аудит, не релиз/установка. Найдены и исправлены:

1. Общий refresh/join сразу отмечает активное имя: если эффект снят, лицензия истекла,
   провайдер отключён или участник вышел из клана ДО первого heartbeat, кадр снимается
   на ближайшем heartbeat, а не ждёт восьмого статического обновления.
2. Смена стадии входа принудительно обновляет имя/шапку даже при refresh=0 и
   dashboard-animation=false. Прежние приватные поля не застревают после потери входа;
   это изменение представления, не обход/переписывание авторизации.
3. Пользовательский header/footer с player_tagged получает декорированный ник на
   каждой перерисовке; чередования со строкой без меток больше нет.
4. Join/quit refresh объединяется в одну отслеживаемую задачу на ближайший тик.
   Reload/shutdown отменяют её вместе с таймерами и probes. Отложенная задача не
   может воскресить выключенный TAB. При массовом одновременном входе нет отдельного
   полного прохода онлайн-списка на каждого входящего.
5. При освобождении TAB удаляются только ещё совпадающие с нашим последним кадром
   имя/header/footer. Уже установленное внешним плагином оформление не стирается.
   Во время работы проверяется фактический header/footer, так что cache не скрывает
   чужую перезапись даже при постоянном авторском тексте.
6. Быстрые активные и обычные player_tagged имена не строят полный контекст;
   скрытая/пустая шапка не читает персональный header-контекст. Для каждой группы
   строк массив placeholders собирается один раз, а не заново для каждой строки.
   Недоступный TPS отмечается неизвестным, а не выдуманными 20 TPS.

Новый TabLifecycle282Test запускает настоящий TabListService через внутренний порт
окружения: управляемые часы, очереди задач и Player-компоненты в памяти. Проверены
14 сценариев: снятие/expiry до первого heartbeat, auth-переходы, custom player_tagged
в шапке, hidden header, чужая перезапись/снятие владения, disable/late task, 200 join
за один тик, 30 reload подряд, все основные probe-ветки, доступ/лимиты, возврат к
custom-формату, quit и отзыв admin-permission, dedup постоянных кадров. Число задач,
кэшей, полных контекстов, декораторов и отправок проверяется утверждениями.

**Границы доказательства:** это детерминированный компонентный прогон реального
сервиса, а не Minecraft-сервер, сетевой клиент или измерение production MSPT/трафика.
Прежняя RGB-матрица и финансовые тесты сохранены; live-сценарий выше остаётся
обязательным перед установкой. Суммы BP 17 400/8 700/26 100 = 52 200 💠, лицензии,

## RC.6: проверка обновления со стабильной 1.4.281

По выбору владельца выполнен следующий аудит совместимости, без релиза/установки.

### Найдено и исправлено

- BP ранее обновлял stock weeks через getConfig()/saveConfig(): без отдельного
  backup, а saveConfig() может поглотить ошибку записи. Теперь BattlePassStockMigration
  строго читает реальный YAML без наследования defaults, сопоставляет точный список
  прежнего stock, делает побайтовый backup и атомарно заменяет файл с force записей.
  Меняется только battlepass.weeks. Даты, названия сезона, настройки и авторские
  задания/суммы не переписываются; повторный запуск не меняет уже обновлённый файл.
- Отсутствующий/неверный weeks и season-start не берутся незаметно из JAR. Пустой
  явный weeks: [] допустим и отключает сезон. Проверяются даты и порядок end/start.
  Ошибка даты больше не создаёт временный сезон с epoch=0 (другую область receipts).
- При невалидном конфиге/ошибке миграции configReady=false блокирует использование BP,
  но не серверную авторизацию/остальную игру. При первом старте аддон выключается
  до исправления; при неудачном reload сохраняется прежнее состояние прогресса,
  закрываются старые окна, администратор получает явный отказ вместо «reload успешен».
- При неподтверждённом результате после atomic replace файл проверяется при следующем
  reload: либо старый stock мигрирует, либо уже новый остаётся без повторной записи.
  Квитанции денег/буста при этом не сбрасываются. Atomic move/force должны поддерживаться
  файловой системой. На symlink stock-конфиг автоматически не заменяется: нужна ручная
  миграция целевого файла. За время подготовки перед replace повторно проверяется,
  что исходный файл не изменился. Не редактировать конфиг параллельно с reload.

### Новые независимые проверки

- Реальная файловая миграция 281→RC6; все прежние snapshots; точный backup,
  неизменные чужие поля/даты и no-op повтор; custom money/target/id/description,
  пустые волны, invalid YAML/date/missing fields; faults до backup/после backup/
  до replace/после replace, очистка tmp, правка владельца и symlink.
- Старый progress/claims/name/wave/неизвестные ID сохраняются после обновления и
  рестарта; сама миграция не трогает остальные JSON-домены. Проверена отдельная
