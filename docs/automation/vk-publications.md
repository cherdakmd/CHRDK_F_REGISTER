# Автоматические новости ВКонтакте

## Что готово и что ещё не включено

`VK news and server tips` работает **в GitHub Actions, не на Minecraft-сервере**.
По умолчанию реальная отправка выключена. Внедрение кода, выпуск ZIP, установка
игрового комплекта и включение публикаций — разные действия.

- Новости — после успешного workflow `Release`, только для стабильного тега
  `v1.*.*` с загруженным непустым основным ZIP и отдельной заметкой игрокам.
- Советы/возможности/напоминания — **среда и воскресенье, 18:00 Europe/Moscow**.
  Cron `0 15 * * 0,3` задан в UTC. GitHub может задержать/пропустить запуск;
  допустимая задержка — 24 часа. Пропуски не догоняются пачкой.
- 16 тем последовательно чередуются по календарным слотам; цикл — 8 недель.
  Повтор запуска того же слота не выбирает другую тему.
- PNG 1280×720: фирменный фон, геометрический алмаз, рубрика, заголовок и подпись.
  Не используются платные генераторы, чужие игровые текстуры или внешние картинки.

## Однократная настройка владельцем

В Settings → Secrets and variables → Actions этого репозитория:

| Тип | Имя | Значение |
|---|---|---|
| Secret | `VK_NEWS_ACCESS_TOKEN` | Отдельный **пользовательский** токен администратора сообщества для официального VK API, разрешающий публикацию стены и загрузку фото |
| Variable | `VK_NEWS_GROUP_ID` | Положительный числовой ID сообщества, без минуса/`club`/URL |
| Variable | `VK_AUTOPUBLISH_ENABLED` | Сначала отсутствует или `false`; только после превью — `true` |

**Токен сообщества из CHRDK_VK не подходит:** схема VK API у `wall.post`,
`photos.getWallUploadServer` и `photos.saveWallPhoto` требует пользовательский
токен. Не подменяйте им токен игрового плагина. Выдавать доступ следует через
официальный OAuth своего разрешённого VK-приложения: конкретный доступ зависит
от типа приложения и прав администратора в группе. Не используйте сайты выдачи
чужих ключей, пароль пользователя или токен в URL команды/issue/переписке.
Права `wall`/`photos` и действительность токена надо проверить при подключении;
если приложение или политика VK не разрешают методы — публикация остановится,
обходов ограничений нет. При истечении/отзыве токен обновляется только в Secret.

Требуются включённые GitHub Actions и Issues. Workflow получает `contents: read`
и `issues: write`; не нужны PAT GitHub, запись в git или доступ к игровому хосту.
Журналы Issues публичны, если репозиторий публичный: они содержат только ключи,
хеши, публичные ID фото/постов и статусы. Секретов и данных игроков там нет.

### Сначала превью

1. В Actions открыть `VK news and server tips` → Run workflow на **main**.
2. Оставить `publish=false`; выбрать `tip`, либо `news` и существующий релизный тег.
3. Скачать artifact `vk-post-preview-…`: `post.txt`, `card.png`, `metadata.json`.
   Превью не обращается к VK и не создаёт/меняет журналы. Для новости читает
   GitHub release и заметку **из самого тега**, не произвольный файл PR.
4. Проверить группу, права OAuth и картинку. После этого выставить
   `VK_AUTOPUBLISH_ENABLED=true`. Реальная пробная публикация — отдельное действие;
   доступность метода не заявляется проверенной офлайн-тестами.

Локально (без токенов и сети):

```bash
python3 -m venv .venv
.venv/bin/pip install -r tools/social/requirements.txt
# Нужны системные DejaVu Sans/DejaVu Sans Bold (fonts-dejavu-core).
.venv/bin/python tools/social/run.py --check
.venv/bin/python tools/social/run.py --at 2026-11-01T18:00:00+03:00
.venv/bin/python tools/social/run.py --news-version 1.4.272
.venv/bin/python -m unittest discover -s tools/social -p 'test_*.py' -v
```

`--at`/`--news-version` разрешены только для превью, не отправки. Выходные файлы
лежат в игнорируемом `social-preview/`, а не коммитятся в репозиторий.

## Откуда берётся текст

Советы — **точные выдержки актуальной вики** из `tools/social/topics.json`.
Публичные `{{fact:…}}` раскрываются через существующий allowlist `FactBook` из
конфигов. Произвольное чтение конфигурации/токенов не поддерживается. Если страница,
выдержка или смысловая сверка вики устарели — отправка останавливается до review.
Все 16 карточек проверяются на переполнение текста в CI.

На каждом совете есть ссылка в вики и оговорка о стандартных настройках проекта:
из исходников нельзя установить, какой комплект и какие кастомные цены сейчас
на живом сервере. Сезонные даты и цены не придумываются автоматически.

Для новой версии автор PR добавляет **короткую заметку игрокам**
`docs/social/releases/<версия>.json`: `version`, `title`, `caption`, 1–6 `points`.
CI требует заметку для текущего `plugin_version`. Технические release notes,
коммиты, WAL/ошибки сборки и произвольный release body в пост не копируются.
Публикация автоматическая, но смысловой текст проходит обычное review исходников.
В новость всегда добавляется: **выпуск комплекта не равен установке на сервер**.
Нельзя писать «уже установлено», пока установка отдельно не подтверждена.

## Дубли, ошибки и восстановление

Один workflow сериализует отправки через общую concurrency-группу. GitHub может
заменить ожидающий запуск более новым; пропущенную новость можно повторно запустить
вручную с тем же тегом, не обходя журнал. Новый совет нельзя вручную «вытолкнуть»
вне актуального слота; используйте превью или следующий календарный запуск.

У каждой записи постоянные ключ, VK `guid` и видимый служебный хеш-хештег.
В Issues `[CHRDK VK <group-id>] YYYY-MM` хранятся месячные JSON-журналы.
Поиск учитывает **открытые и закрытые** журналы всех месяцев; один релиз не
публикуется заново при смене месяца или редактировании заметки. Не удаляйте
журналы/маркеры. Не включайте параллельно второй независимый публикующий workflow.
Кэш Actions не используется как единственное хранилище.

Порядок: проверить журнал/стену → загрузить картинку → сохранить `prepared` →
подтвердить `posting` в GitHub → `wall.post` → подтвердить `posted` с ID записи.
Не отправляем текст без картинки при сбое загрузки. Явные ответы VK по лимиту
6/9 повторяются ограниченно. Ошибки доступа, captcha и неизвестные ответы не
обходятся; URL загрузки, HTTP-ответы и параметры не печатаются в лог.

При таймауте/сбое подтверждения `wall.post` следующая попытка сначала ищет маркер
среди 1000 свежих собственных записей стены. Нашла — завершает журнал без нового
поста. Не нашла — **не повторяет отправку вслепую**, блокирует последующие новые
публикации и требует ручного разбора. Это сознательный выбор против двойных постов.

При `posting` без найденного маркера оператор проверяет стену/отложенные записи,
целевую группу и журнал. Если пост есть — вписывает подтверждённый `post_id` и
`status: posted`, сохраняя исходный ключ/digest. Если достоверно установлено, что
поста нет и исходный запрос завершён, может вернуть **эту** запись в `prepared`
и повторить исходный тег/слот. Не удалять весь журнал ради «починки». Если
подготовленный текст/PNG изменился, сначала сверить старый результат и digest,
а не сбрасывать защиту. Повреждённый JSON, дубли ключей или недоступный журнал
останавливают отправку до любых новых записей стены.

### Аварийная остановка

Установить `VK_AUTOPUBLISH_ENABLED=false`, отменить уже запущенный job (изменение
Variable не останавливает его мгновенно), при необходимости отозвать токен в VK.
Журналы сохранить для восстановления. После отмены во время `wall.post` сначала
разобрать `posting`, а не сразу включать отправку. Посты не удаляются автоматически.

## Источник контракта VK API

Проверено по официальной схеме VKCOM/vk-api-schema:
- https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json
- https://github.com/VKCOM/vk-api-schema/blob/master/photos/methods.json

Используется API 5.199, отдельный клиент вне CHRDK_VK; живой доступ к VK при
разработке не проверялся. Minecraft-сервер, его данные и TradeMC не меняются.
