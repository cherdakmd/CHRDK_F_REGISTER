# Новости и советы в беседу ВКонтакте

## Что изменилось

Автоматизация `VK news and server tips` работает **в GitHub Actions, не на Minecraft-сервере**.
С версии 1.4.275 она отправляет **текст и PNG в одну выбранную беседу от сообщества**,
а не публикует на стене. Используется ключ сообщества. Прежний путь стены оказался
несовместим с ним: живая проверка `wall.get` завершилась кодом 27 до загрузки фото.
Пересылка сообщения возможна; это **не штатный репост записи стены**. Чтобы выложить
материал на стену, нужно отдельно опубликовать текст и картинку вручную.

- Советы/возможности/напоминания — **ежедневно в 12:00 и 18:00 Europe/Moscow**.
  Cron `0 9,15 * * *` задан в UTC. GitHub может задержать/пропустить запуск;
  актуальность слота — менее 6 часов, старые слоты не догоняются пачкой.
- 16 тем последовательно чередуются по календарным слотам, цикл — 8 дней.
- Новости релизов — отдельно, после успешного `Release` своего репозитория:
  стабильный тег `v1.*.*`, непустой загруженный основной ZIP, заметка игрокам
  `docs/social/releases/<версия>.json` **из самого тега**, привязка к собранному commit.
  Выпуск не означает установку на игровой сервер.
- PNG 1280×720 сохраняет выбранный игровой фон: AI-иллюстрация, не скриншот сервера.
  Локальный рендер не использует платные API. Полные объяснения остаются в тексте.
- До успешной проверки и явного решения владельца **`VK_AUTOPUBLISH_ENABLED=false`**.
  Код, выпуск ZIP, установка плагинов и включение рассылки — разные действия.

## Настройка владельцем

Settings → Secrets and variables → Actions:

| Тип | Имя | Значение |
|---|---|---|
| Secret | `VK_NEWS_ACCESS_TOKEN` | Ключ нужного сообщества с доступом к сообщениям и фотографиям |
| Variable | `VK_NEWS_GROUP_ID` | Положительный ID сообщества, сейчас `237779683` |
| Variable | `VK_NEWS_PEER_ID` | ID беседы **для бота**, получить через `find_chat` ниже |
| Variable | `VK_AUTOPUBLISH_ENABLED` | Пока `false`; `true` — только после успешного теста и решения владельца |

Не отправляйте токен в чат, не кладите его в Variables/файлы, не меняйте игровой
ключ CHRDK_VK. OAuth, чужие приложения и генераторы токенов для этой схемы не нужны.
При отзыве/истечении ключа обновляется только Secret. Наличие ключа не гарантирует
членство бота в конкретной беседе, право писать, читать историю или загружать фото:
это проверяется отдельно. Ошибки показывают только имя метода и числовой код.

### 1. Добавить сообщество и найти правильный ID

1. В настройках сообщества включить сообщения, возможности ботов и разрешение
   добавлять сообщество в беседы, если соответствующие переключатели доступны.
2. Добавить **именно это сообщество** в нужную беседу. Проверить право отправлять
   сообщения и доступ к истории. Если VK требует дополнительные права для чтения
   истории, настройте их в беседе; без истории безопасная отправка запрещена.
3. Написать в нужную беседу отдельным сообщением **`#chrdk-news-setup`**.
   До завершения поиска не писать следом: маркер должен быть последним сообщением.
4. В Actions → `VK news and server tips` → Run workflow выбрать **main**:
   `mode=find_chat`, `publish` выключен, `kind=tip`, `release_tag` пустой.
5. В шаге `Find marked chat without sending messages` / Annotations появится
   **`VK_NEWS_PEER_ID=…`**. Сохранить число в Variable с этим именем.
   Результат также есть в `connection.json` артефакта `vk-post-preview-…`.

**Не вычисляйте этот ID по своему `sel=cNN` в адресной строке VK**: локальный
номер беседы у пользователя и у бота может отличаться. Режим поиска читает
`messages.getConversations`, но не выводит названия, участников или тексты чужих
бесед. Пишет только ID единственного чата с маркером от пользователя и правом
отправки. Не отправляет сообщения, не меняет Variables и журнал публикаций.
При 0/нескольких совпадениях или исчерпании лимита 1000 диалогов останавливается;
не выбирает первую случайную беседу. Маркер не является секретом или паролем.

### 2. Проверить доступ без отправки

Run workflow на **main**: `mode=check_connection`, `publish` выключен,
`kind=tip`, `release_tag` пустой. Вызовы:

- `messages.getConversationsById`: ровно нужная беседа, `can_write.allowed=true`;
- `messages.getHistory`: история доступна для сверки дублей;
- `photos.getMessagesUploadServer`: допустимый HTTPS-адрес, **файл не загружается**.

Результат — `connection.json`, без API-ответов и подписанных URL. Это не доказывает
работу `photos.saveMessagesPhoto` / `messages.send`: они проверяются следующим шагом.

### 3. Одно настоящее тестовое сообщение

Run workflow на **main**: `mode=test_post`, `publish` выключен, `kind=tip`,
`release_tag` пустой. После preflight отправляются один текст и карточка в указанную
беседу. Режим **не включает расписание и не меняет Variables**.

Ключ `test:<версия>` постоянен для данной версии и получателя: повторный запуск
не должен создавать новое сообщение. Новая версия или другая беседа — отдельный
тест. При неоднозначном исходе см. восстановление ниже, не сбрасывайте журнал.

### 4. Включить только после проверки

Проверить текст и картинку в беседе. Затем, только по решению владельца,
выставить `VK_AUTOPUBLISH_ENABLED=true`. Чтобы остановить рассылку — снова `false`.
Обычная ручная отправка: `mode=preview`, `publish=true`, нужные `kind`/тег;
она тоже требует разрешающего флага. Проверочные режимы несовместимы с `publish=true`.
GitHub Actions/Issues должны быть включены; workflow использует `contents: read`
и `issues: write`, без PAT и доступа к игровому хосту.

## Превью без VK

`mode=preview`, `publish=false`: artifact содержит `post.txt`, `card.png`,
`metadata.json`. Для `tip` VK/GitHub-журнал не вызываются; для `news` читаются
релиз и заметка из тега, но VK и журнал не меняются. Для старого тега без заметки
рассылка запрещена. Выбор `news` с пустым тегом — ошибка, для простого примера нужен `tip`.

Локально:

```bash
python3 -m venv .venv
.venv/bin/pip install -r tools/social/requirements.txt
.venv/bin/python tools/social/run.py --check
.venv/bin/python -m unittest discover -s tools/social -p 'test_*.py'
.venv/bin/python tools/social/run.py --at '2026-11-01T18:00:00+03:00'
.venv/bin/python tools/social/run.py --news-version 1.4.275
```

## Защита от дублей и восстановление

Журнал схемы 2: месячные Issues **`[CHRDK VK CHAT <group> <peer>] YYYY-MM`**,
включая закрытые. Изолирован по сообществу и беседе. Старые журналы стены
`[CHRDK VK <group>]` и чужие беседы **не читаются как подтверждения и не изменяются**.
Не удаляйте журналы и не редактируйте статусы ради повторного запуска.

Состояния: `prepared` → `posting` → `posted`. `posting` обязан сохраниться **до**
`messages.send`. Стабильный ненулевой 31-битный `random_id` зависит от группы,
беседы и ключа; дополнительный маркер сообщения зависит от ключа публикации.
Таймауты не вызывают слепой повтор. Повторы API ограничены явными кодами 6/9.

Сверка просматривает до 1000 последних сообщений выбранной беседы, проверяет
**автора-сообщество, peer_id и отдельную полную строку маркера**. Чужое сообщение
с копией маркера не считается подтверждением. Если `messages.send` вернул 0,
сразу выполняется сверка истории без повторной отправки. В журнале `message_id`
хранит положительное подтверждение VK: обычный ID либо `conversation_message_id`
из истории при отсутствии обычного. Это не универсальная ссылка на сообщение.

Не найдено подтверждение прежнего `posting` — **вся новая отправка в эту беседу
блокируется** до ручной сверки. Это намеренная безопасность, в том числе когда
сообщение удалено или старше окна 1000. Найденный маркер восстанавливает `posted`
без новой загрузки/отправки. Повреждённый/дублированный журнал не сбрасывается.

В публичных Issues остаются только группа/peer, ключи, хеши, статусы и номера
подтверждений — без сообщений, участников, токенов и вложений. `access_key` фото
передаётся VK только в памяти и **никогда не записывается в Issue/артефакт/лог**.
После сбоя до `posting` фото может загружаться повторно; это не дубль сообщения.
Подписанный upload URL не логируется, HTTP-редиректы запрещены.

### Ручная сверка и аварийная остановка

При неизвестном `posting` сначала установить флаг в `false` и дождаться окончания
или отменить активный job: изменение Variable не отменяет уже выполняющийся код.
При компрометации отозвать ключ VK. Журнал сохранить. Проверить нужную беседу,
сообщество-автора, полный маркер, текст и карточку. Если сообщение действительно
есть, оператор может записать подтверждённый положительный ID и `status: posted`
в **эту** запись, не меняя её ключ/digest и принадлежность группе/peer. Отсутствие
сообщения в последних 1000 — не доказательство неотправки; автоматически возвращать
`posting` в `prepared` или удалять журнал нельзя. Неоднозначность требует отдельного
разбора, а не нового ключа для обхода защиты. Сообщения автоматически не удаляются.

## Контракт API и границы проверки

Официальная схема VK допускает community token для `messages.send`,
`messages.getHistory`, `messages.getConversations`, `messages.getConversationsById`,
`photos.getMessagesUploadServer`, `photos.saveMessagesPhoto`:
[сообщения](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json),
[фотографии](https://github.com/VKCOM/vk-api-schema/blob/master/photos/methods.json).
Клиент использует API 5.199 и не разрешает методы стены. Офлайн-тесты не доказывают
живой доступ конкретного ключа/беседы; он подтверждается только шагами 2–3.
Minecraft-плагин, данные сервера и TradeMC эта автоматизация не меняет.
