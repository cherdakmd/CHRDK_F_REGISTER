# CHRDK_Claims: аудит релиза 1.4.73, исправления и доработки 1.4.74–1.4.79

Документ фиксирует разбор модуля **CHRDK_Claims** из релиза **v1.4.73**
(`chrdk-claims-1.4.73.jar`, Purpur 26.3 / Minecraft 26.3, Java 25), найденные дефекты,
внесённые исправления и доработки. Исходной точкой служит тег `v1.4.73`; все ссылки
на строки даны по этому тегу.

## 1. Резюме

Модуль закрывает базовый сценарий «приват чанка за алмазы»: покупка, рента, казна,
участники, продажа игрокам, выкуп сервером, ASCII-карта и защита территории. Экономика
и UI сделаны аккуратно, но в четырёх местах поведение расходилось с документацией,
а в двух — могло привести к потере денег или данных:

## 3. Критичные дефекты

### C-01. Рента: долг не возвращался

`ClaimsService.processUpkeep` (v1.4.73, строки 362–395) вёл себя так:

```java
if (store.takeTreasury(claim.owner, cfg.upkeepPerDay)) {
    claim.paidUntil += DAY;   // день оплачен
    claim.debtDays = 0;       // любой успешный день обнуляет всю историю
} else {
    claim.paidUntil += DAY;   // день НЕ оплачен, но граница сдвинута
    claim.debtDays++;         // ...и долг растёт
}
```

Последствия:

- `paidUntil` сдвигался и за неоплаченные сутки, поэтому после пополнения казны
  пропущенные дни уже никто не выставлял — долг «растворялся»;
- первое же успешное списание (например, через сутки) обнуляло `debtDays`, хотя
  прошлые сутки остались неоплаченными;
- при простое сервера цикл мог прокрутить тысячи суток (вплоть до 20 000+ при
  испорченной дате `paidUntil = 0`).

**Исправление.** Чистая функция `ClaimMath.settleRentDay`:

1. из казны сначала гасится накопленный долг (пока хватает денег);
2. затем оплачивается текущая сутки;
3. если после этого долг всё ещё есть — добавляется новая сутки;
4. `released = debtDays > graceDays`.

`ClaimsService.processUpkeep` применяет её по одной сутке на чанк, поэтому долг
возвращается при первом пополнении, а не прощается. «Догон» ограничен
`ClaimMath.MAX_CATCHUP_DAYS = 400`; при большем простое/испорченной дате остаток
сдвигается к текущему моменту с предупреждением в лог. Уведомления о долге и утрате
чанка теперь уходят **сразу**, если владелец онлайн и авторизован, иначе — в
отложенные вести (как раньше).

### C-02. Повреждённый JSON затирался

`ClaimStore.load` (v1.4.73, строки 52–114) при ошибке чтения писал warning и оставлял
пустые коллекции. Через минуту `saveAsync` записывал пустой `claims-data.json` поверх
исходного — все приваты и казна терялись безвозвратно.

**Исправление.** При любой ошибке чтения/разбора файл **перемещается** в
`claims-data.json.corrupt-<millis>`, в лог пишется SEVERE с путём и подсказкой про
`claims-data.json.bak`. Плагин стартует с пустыми приватами, но данные остаются на
диске. Ошибки отдельных записей (нет владельца/мира, дубликаты чанков, `paidUntil = 0`)
обрабатываются точечно и не роняют весь файл.

### C-03. Надёжность записи

Было: `Files.move(tmp, file, REPLACE_EXISTING)` без атомарности, без резервной копии,
снимок собирался и писался под общим `synchronized` (главный поток ждал диск),
а асинхронный поток читал изменяемые поля `Claim` без синхронизации.

**Исправление.** Снимок собирается под блокировкой (копии полей и списков), запись
идёт вне блокировки: временный файл → `ATOMIC_MOVE` (fallback — обычная замена) →
предыдущая версия остаётся в `claims-data.json.bak`. Добавлены `revision` (чтобы не
терять изменения, пришедшие во время записи) и `AtomicBoolean saving` (без
параллельных сейвов). В файл пишется `version: 2`.

| Костная мука | `BlockFertilizeEvent` не обрабатывался — чужая ферма ускорялась и портилась | отмена для игрока |
| Книга с кафедры | `PlayerTakeLecternBookEvent` не обрабатывался | отмена |
| Лодки/вагонетки/кристаллы/стойки | `EntityPlaceEvent` не обрабатывался | отмена |
| Стрижка животных | `PlayerShearEntityEvent` не обрабатывался | отмена |
| Торговля с виллагером | `Villager` не входил в список сущностей | отмена |
| Наковальня/маяк/якорь/торт/TNT/свечи/кашпо/компостер | `PlayerInteractEvent` отменялся только для контейнеров, дверей и (опционально) редстоуна | флаг `protect.workstations` (вкл.) |
| Яйца призыва | спавн моба в чужом привате | отмена использования яйца |
| Воронка из двойного сундука | `DoubleChest` — не `BlockState`, `holderBlock` возвращал `null` | позиция берётся из `Inventory#getLocation()` |
| Воронка снаружи в чужой сундук | проверялся только источник | проверяются источник **и** приёмник |
| Песок/гравий/наковальня падают в приват | `EntityChangeBlockEvent` отменял всё, включая `FallingBlock` | падающие блоки пропускаются |
| Рамки при взрыве/физике | флаги `entities`/`explosions` игнорировались | причина разбирается: `ENTITY` → личный виновник, `EXPLOSION` → `protect.explosions`, остальное → `protect.entities` |
| Поршни на втягивании | проверялся только сам блок, а «назначение» считалось в сторону от поршня | проверяются обе клетки, назначение — через `getOppositeFace()` |
| Яйцо дракона, хранилище, подозрительные песок/гравий | клик не считался «использованием»: яйцо телепортировалось из привата, хранилище тратило ключи, археология отдавала добычу | добавлены в `WORKSTATIONS` |
| Взрыв убивал питомцев, скот и стойки | `EntityExplodeEvent`/`BlockExplodeEvent` защищали только блоки | взрывной урон животным, стойкам, рамкам и транспорту в привате отменяется (`protect.explosions`) |

Дополнительно: отказ теперь показывается и при затаптывании грядки, а карта
`denyNotified` очищается при выходе игрока (мелкая утечка памяти).

## 5. Экономика, команды и UX

- **Авторизация.** `unclaim` и `sellback` теперь требуют `general.require-auth`,
  как и остальные операции. Проверяется право `chrdkclaims.use` (или
  `chrdkclaims.admin`), которое раньше было декоративным.
- **Продажа.** Покупатель на чужом продающемся чанке получает подсказку с ценой и
  `/claim buy`; участники получают отложенную весть о потере доступа; продавец — одно
  уведомление, а не два.
- **`/claim sell`** без аргумента больше не снимает чанк с продажи: показывается
  подсказка, снятие — только `/claim sell снять`.
- **Передача.** Новая команда `/claim transfer <ник>`: владелец передаёт текущий чанк,
  проверяются лимит и существование игрока; получателю уходит сообщение/весть.
- **Участники.** `/claim add` проверяет, что игрок уже заходил на сервер (защита от
  опечаток), и уведомляет его; при `all` и нуле изменений больше не пишет «добавлен
  в 0 приватов».
- **Казна.** Взнос сообщает, сколько нужно и сколько есть (`deposit-not-enough`);
  выдача/выкуп сообщают, если часть предметов выпала на землю.
- **`/claim balance`** показывает ближайшую дату ренты, казну и необходимую сумму.
- **`/claim map`** использует `general.map-radius` (2..8) и настраиваемую строку
  `map-line` (цвет/формат через `messages.yml`).
- **`/claim info`** сообщает, владелец вы или участник.

## 7. Ресёрч: как это делают другие и какие события нужны

**GriefPrevention** строит приваты на «claim blocks», которые начисляются за активное
время, покупаются/продаются через Vault, а `/transferclaim` передаёт участок другому
игроку; продажа/аренда участков вынесена в сторонние аддоны (GP RealEstate,
RealEstate), где сделка оформляется табличкой и переводит владение/аренду. Наш модуль
проще (фиксированная цена за чанк, рента из казны, налог с P2P-сделки), но термины и
сценарии совпадают: лимит, передача, продажа, аренда/рента, возврат серверу.

- GriefPrevention: начисление и покупка блоков, `/transferclaim`, лимиты
  <https://github.com/GriefPrevention/GriefPrevention/wiki>
- GP RealEstate (продажа/аренда/лизинг участков через таблички)
  <https://www.gpdoes.org/wiki/plugins/gpre>
- RealEstate для GriefPrevention (аренда с автоматическим продлением)
  <https://www.spigotmc.org/resources/realestate.66966/>

**Paper-события**, которыми закрыты лазейки (все доступны в API 26.3):

- `PlayerHarvestBlockEvent` — сбор урожая без разрушения блока
  <https://jd.papermc.io/paper/1.21.11/org/bukkit/event/player/PlayerHarvestBlockEvent.html>
- `BlockFertilizeEvent` — костная мука; `getPlayer()` может быть `null` (разбрасыватель)
  <https://jd.papermc.io/paper/1.21.11/org/bukkit/event/block/BlockFertilizeEvent.html>
- `PlayerTakeLecternBookEvent` — вынимание книги с кафедры
  <https://jd.papermc.io/paper/1.21.11/org/bukkit/event/player/PlayerTakeLecternBookEvent.html>
- `EntityPlaceEvent` — установка лодок, вагонеток, кристаллов, стоек
  <https://jd.papermc.io/paper/1.21.11/org/bukkit/event/entity/EntityPlaceEvent.html>
- `PlayerShearEntityEvent`, `EntityDamageByEntityEvent`, `HangingBreakEvent` — животные,
  рамки и их причины исчезновения
- `InventoryMoveItemEvent` — воронки; `Inventory#getLocation()` корректен и для
  `DoubleChest`, в отличие от `InventoryHolder instanceof BlockState`

Отдельно проверено, что `HangingBreakEvent.RemoveCause` различает `ENTITY`,
`EXPLOSION`, `PHYSICS` и `OBSTRUCTION`, поэтому одну и ту же защиту можно привязать к
разным флагам без «глухого» запрета.

## 10. Что осталось за рамками

Намеренно **не** делалось в этом изменении (крупные архитектурные шаги):

1. **UUID вместо ника.** Приваты и казна по-прежнему ключуются ником: смена ника
   Minecraft «теряет» владение. Правильное решение — хранить `ownerId` (UUID) рядом с
   ником и мигрировать старые записи; это отдельный PR с миграцией схемы.
2. **MySQL/сеть серверов.** `claims-data.json` достаточен для одного сервера; для
   Velocity/BungeeCord нужен общий стор и гейт на прокси.
3. **GUI/GriefPrevention-совместимость.** Продажа табличками и аренда с автопродлением —
   следующий уровень UX; визуализация границ частицами (`/claim borders`, 1.4.75) и
   роли участников (1.4.78) уже сделаны.
4. **Аренда чанков игроками.** Сейчас есть только рента серверу и продажа; аренда
   «игрок → игрок» (как в RealEstate) потребует отдельного журнала платежей.
5. **PlaceholderAPI.** `%chrdkclaims_chunks%`, `%chrdkclaims_debt%` для таб-листа и
   скорбордов.

## 11. Совместимость и миграция

- Данные: старый `claims-data.json` читается как есть (нет `version` → считается
  версией 1); при сохранении появляется `version: 2` и резервная копия `.bak`.
- Конфиг: новые ключи необязательны; значения по умолчанию сохраняют прежнее
  поведение, кроме `protect.workstations` (защита вёрстаков включена — это осознанное
  усиление) и появившегося фильтра миров (пустые списки = все миры).
- Сообщения: новые ключи автоматически добираются из ресурса плагина, старый
  `messages.yml` продолжает работать; `/claimadmin reload` покажет замечания.
- Требования: ядро CHRDK_Core ≥ 1.4.6 (публичный API), Purpur 26.3 / Java 25.

## 12. Доработки 1.4.75: рынок, лимиты и границы

После закрытия дефектов C-01…C-18 модуль получил следующий уровень UX и
эксплуатационных возможностей. Все изменения — обратно совместимые: новые ключи
`messages.yml` подтягиваются из ресурса, `claims-data.json` читается без миграции.

### 12.1. Витрина продаж и страницы

- `ClaimMarket` — чистая сортировка лотов: сначала текущий мир, затем расстояние в
  чанках, затем мир и координаты. Расстояние для чужого мира не вычисляется
  (`Integer.MAX_VALUE`), в сообщении остаётся пустой сегмент.
- `Pagination` — общая постраничная выдача: `pageCount`, `clampPage`, `slice`;
  номер страницы с единицы, мусор и отрицательные значения трактуются как первая,
  слишком большие зажимаются последней.
- `/claim forsale [страница]` — 8 лотов на страницу, строка «страница N/M» с
  кликабельным переходом; пустая витрина подсказывает `/claim sell <цена>`.
- `/claim list [страница]` — стабильный порядок (мир, x, z), чтобы страницы не
  «прыгали» между вызовами; заголовок по-прежнему показывает `N/лимит`.

### 12.2. Персональные лимиты

- `ClaimStore.limits` (необязательный блок `limits` в JSON): `limitOverride`,
  `setLimitOverride` (зажатие 1..100000), `clearLimitOverride`, `limitOverrides`.
- `ClaimsService.baseLimitOf` — база + бонус проходки; `limitOf` отдаёт персональный
  лимит, если он назначен (он главнее и базы, и бонуса).
- `/claimadmin limit <ник>` — показать фактический и общий лимит; `limit <ник> <n>` —
  назначить; `limit <ник> сброс` — снять. При понижении ниже текущего количества
  чанков игрок получает предупреждение (онлайн — сразу, офлайн — вестью после входа),
  приваты не удаляются.
- Подсказка «с проходкой — больше» больше не показывается игрокам с персональным
  лимитом: она к ним не относится.

### 12.3. Смена ника

`ClaimStore.transferAll(from, to)` и `/claimadmin transferall <от> <кому>` переносят
приваты (владение), казну (с суммированием остатка получателя и защитой от
переполнения), отложенные вести и персональный лимит; ники сравниваются без учёта
регистра, получатель удаляется из участников переданного привата. Возвращается
`TransferSummary(claims, treasury, notices, limitMoved)`, по нему строятся отчёты
администратору и весть получателю.

### 12.4. Границы и информация

- С 1.4.257 `/claim borders` — весь связный контур одного владельца без швов:
  `DUST` в три ряда, белые угловые `ELECTRIC_SPARK`, только получателю.
  Свои — зелёные, чужие — золотые, свободный чанк — голубой. Период 0,5 с,
  `general.border-seconds` 10 по умолчанию (3..60). Кэш по ревизии данных,
  512 частиц/импульс с ротацией по всему контуру, без загрузки чанков.
- `general.border-on-own-entry: true`: автоматически владельцу при входе,
  авторизации и возрождении. Отдельный трекер связности не зависит от текстовых
  notice-флагов/кулдауна. Внутренние переходы не перезапускают показ; телепорт на
  несвязанный свой участок запускает. Повтор команды выключает; смерть, выход,
  потеря авторизации и отключение снимают задачу.
- `/claim info` — остаток оплаченных суток (`info-left`) или подсказка, что рента
  спишется в ближайший час (`info-left-today`).

### 12.5. Регистр ника

Казна, персональные лимиты и отложенные вести раньше ключевались ником с учётом
регистра: `/claimadmin limit steve` создавал отдельную запись, невидимую для

## 15. Доработки 1.4.78: роли участников

### 15.1. Модель

`Claim.Role` — три уровня в порядке возрастания прав: `ACCESS` (двери, кнопки,
рычаги, плиты, вёрстаки, открытие таблички), `CONTAINER` (+ сундуки, печки, воронки,
кафедры), `BUILD` (стройка, урожай, костная мука, животные, стойки, транспорт, яйца
призыва). Проверка — через `ordinal()`, поэтому добавление уровня в конец шкалы не
ломает существующие проверки.

- `roleOf(name)`: владелец → `BUILD`; посторонний → `null`; участник без записи →
  `BUILD` (совместимость с 1.4.73–1.4.77, где ролей не было).
- `allows(name, required)`, `canUse`/`canOpen`/`canBuild` — обёртки над одной проверкой.
- `setRole` игнорирует посторонних и не хранит `BUILD` (отсутствие записи = полный),
  `removeMember` и `clearMembers` чистят роли, `explicitRoles` отдаёт только неполные.

### 15.2. Защита

`ClaimProtectionListener.may(player, claim, required)` заменил единственную проверку
`canBuild`: ломание/установка/вёдра/урожай/удобрение/животные/транспорт/огонь/яйца —
`BUILD`; контейнеры и кафедра — `CONTAINER`; двери, редстоун-механизмы, вёрстаки,
открытие таблички — `ACCESS`. `deny` больше не пересчитывает права (иначе игрок с
ролью не видел бы отказ), но обход администратора по-прежнему гасит сообщения.

### 15.3. Команды и данные

`/claim add <ник> [доступ|контейнеры|полный] [все]` — добавление и смена роли одним
вызовом (`role-updated`), `/claim remove` чистит участника вместе с ролью,
`/claim info` печатает роли. В JSON — необязательный блок `mr` («ник в нижнем
регистре» → имя роли); неизвестные роли игнорируются и трактуются как полный доступ.
Продажа, передача и `transferAll` очищают участников и роли.

## 19. Доработки 1.4.147: сообщение о границе всегда

### 19.1. Новые умолчания

- `general.notice-mode: both` — строка действия и чат; причина: строку над
  хотбаром перебивают навыки, достижения и артефакты. Неизвестное значение тоже
  падает в `both`, а не в `actionbar`.
- `general.notice-own: true` — свои приваты сообщаются; `enter-own` показывает
  дату оплаты через новый плейсхолдер `%paid-note%` (пустая строка, если оплата
  неизвестна), поэтому «оплачен до» не висит с пустым значением.

### 19.2. Пересчёт точки, а не забывание

- `refreshNoticeLater(player)` — `updateClaimNotice` через 2 тика после события,
  когда сервер уже перенёс игрока: используется в `PlayerTeleportEvent`,
  `PlayerRespawnEvent` (новый обработчик) и `PlayerAuthCompletedEvent`.
- `PlayerTeleportEvent` больше не вызывает `forget`: прыжок между приватами даёт
  и «выход», и «вход», а прыжок внутри привата ничего не пишет (`sameChunk`).
- `PlayerJoinEvent` — сообщение через секунду (20 тиков), чтобы новичок получил
  его уже на своей случайной точке. Смерть по-прежнему забывает чанк: возрождение
  сообщит точку прибытия, а не приват гибели.
- `ClaimNoticeTracker.sameTerritory` — соседний чанк того же владельца в том же
  мире границей не считается: снимок обновляется молча, «выход» позже называет
  последний чанк. Смена владельца, выход в свободный чанк и другой мир работают
  как раньше. Причина — чат-режим по умолчанию: без этого большой приват заливал
  чат при беге.

### 19.3. Миграция конфига

- `ClaimNoticeMigration.rewrite(List<String>)` → `Result(lines, changed)` —
  чистая построчная правка секции `general`: стоковые `notice-mode: "actionbar"`
  и `notice-own: false` становятся `"both"` и `true`, инлайн-комментарии и
  отступы сохраняются, ключи других секций не трогаются. YAML не
  пересохраняется, поэтому русские комментарии и порядок ключей в config.yml
  остаются на месте (в отличие от `saveConfig`).
- `apply(configFile, dataFolder, logger)` — одноразовый запуск: метка
  `notice-migration.txt` с версией 2 рядом с конфигом, запись через временный
  файл с атомарным переносом. `ClaimsPlugin.reloadClaimsConfig` перечитывает
  конфиг только если файл действительно изменился, и пишет в консоль, какие
  ключи обновлены. Битый маркер считается отсутствующим — повтор безопасен.
