# Автоматическое обновление конфигов ядра и аддонов

**Статус:** реализовано в активной ветке, **без нового релиза**. Дата: 6 ноября 2026 года.
**Решение владельца:** вариант **C (схема версий)**, `messages.yml` обновлять
физически на диске, код — следующим коммитом в этой ветке. Тег `v1.5.2-rc.2`,
его ассеты, `Latest = v1.5.1`, TradeMC, production и живой smoke не менялись.

**Файлы:**
`src/main/java/ru/cherdakmd/chrdkregister/ConfigSchemaEngine.java` — движок,
`src/main/java/ru/cherdakmd/chrdkregister/ConfigUpgrader.java` — обёртка Bukkit,
`src/test/java/ru/cherdakmd/chrdkregister/ConfigSchemaEngineTest.java` — 8 тестов,
`ConfigUpgrader.apply(this)` в `onEnable()` ядра и всех 22 аддонов.

---

## 1. Проблема, которая была до этого

| Что | Как работало | Следствие |
| --- | --- | --- |
| `config.yml` (Core + 22 аддона) | `saveDefaultConfig()` создаёт файл **только если его ещё нет** | Существующий файл никогда не дополняется новыми ключами |
| Чтение новых ключей | Код везде указывает дефолт: `cfg.getBoolean("prestige.enabled", true)` | Механика работает, но владелец **не видит** новый ключ у себя в файле |
| `messages.yml` | `Messages.load/from/fromChecked` объединяет дефолты JAR с оверрайдами **в памяти** | Новые тексты подхватываются, но файл владельца не пополняется |
| Точечные миграции Core | `PresentationMigration`, `PremiumPresentationMigration`, `EconomyTariffMigration` | Обновляют только узкие стоковые секции и только ядро |
| `PluginUpdateService` | Меняет **JAR** в `plugins/update/`, бэкапит JAR и `manifest.json` | Конфиги не трогает совсем |
| Версионирование | Маркера схемы не было | Нельзя отличить «уже обновляли» от «ещё нет» |

После `v1.5.2-rc.2` в `skills/config.yml` не появлялись `prestige.*`, `diamonds.*`
и `excluded-materials`, хотя они уже действовали. Владелец узнавал о новых
ключах только из заметок релиза.

## 2. Инварианты

1. **Владельческие значения не перезаписываются.** Добавляются только
   отсутствующие ключи, скопированные из эталонного ресурса JAR.
2. **Комментарии и форматирование сохраняются.** `YamlConfiguration.save()`
   **не используется**: он переформатирует YAML и удаляет все комментарии.
   Движок работает с текстом и пересчитывает шаг отступа (2 или 4 пробела) под
   файл владельца.
3. **Идемпотентность по маркеру версии.** Дополнение идёт только на переходе
   `vN → vN+1`. Файл с актуальной версией не меняется **вообще** — владелец
   может поправить или даже удалить ключ, и следующий рестарт его не вернёт.
4. **Backup до любой записи** (`config-before-schema-…yml` рядом с файлом) и
   атомарная замена через temp-файл с fallback на обычный `Files.move`.
5. **Fail-safe:** любая ошибка (битый YAML, нечитаемый ресурс, не прошедшая
   проверка результата) оставляет файл владельца нетронутым и пишет `WARNING`.
6. **Не трогаются данные:** только `config.yml` и `messages.yml`, не `*.json`,
   playerdata, миры и банковские квитанции.
7. **Публичный API не меняется:** `API_VERSION` остаётся 42, классы лежат в ядре
   рядом с `Messages`, аддоны уже имеют `depend: [CHRDK_Core]` и
   `compileOnly project(':')`.

## 3. Как это работает

Вызов стоит **сразу после `saveDefaultConfig()`** и **до чтения конфига** в
каждом `onEnable()`:

```java
saveDefaultConfig();
ConfigUpgrader.apply(this);
```

В ядре вызов стоит после `PresentationMigration`/`PremiumPresentationMigration`
(иначе их `YamlConfiguration.save()` перезаписал бы результат) и перед
`PluginConfig.fromBukkitConfig(getConfig())`.

### Маркеры версии

| Файл | Маркер | Почему |
| --- | --- | --- |
| `config.yml` | корневой ключ `config-version: 1` | лишний корневой ключ безвреден, код читает конфиг по именам |
| `messages.yml` | комментарий `# messages-version: 1` | **не ключ**: `Messages.flatten` разворачивает единственную верхнюю секцию, и второй корневой ключ превратил бы все тексты в `messages.*` |

Файл без маркера считается `v0` (создан до появления схемы): при первом старте
после обновления в него дописываются все новые ключи и ставится `v1`. Файл с
версией **выше**, чем в JAR (откат сборки), пропускается без правок.

### Целевая версия и карты миграций

Необязательный ресурс `config-schema.yml` в JAR модуля:

```yaml
config-version: 2
messages-version: 1
migrations:
  config:
    2:
      rename:
        prestige.xp-per-step: prestige.xp-bonus
      remove:
        - legacy.dead-key
  messages:
    2:
      remove:
        - obsolete-announce
```

- `rename` переносит **владельческое значение** под новое имя (смена только
  внутри одной секции);
- `remove` удаляет устаревший ключ вместе с его потомками;
- после карт выполняется аддитивное дополнение по эталону;
- маркер обновляется до целевой версии.

Если ресурса нет, действует базовая **v1 без переименований**. Сейчас ни у
одного модуля нет `config-schema.yml`: все ключи `v1.5.2-rc.2` (`prestige.*`,
`diamonds.*`, `excluded-materials`, `anvil.*`, тексты престижа) уже есть в
эталонных ресурсах, поэтому переход `v0 → v1` просто дописывает их в файлы
владельцев.

> **Дисциплина для будущих релизов:** меняя набор ключей в
> `src/main/resources/config.yml` или `messages.yml`, в том же коммите добавьте
> (или поднимите) `config-schema.yml` с новой версией и картой миграций. Без
> подъёма версии новые ключи не будут дописаны — это сделано намеренно, чтобы
> не возвращать владельцу намеренно удалённые ключи при каждом рестарте.

### Триггер

Обновление JAR через `PluginUpdateService` не имеет доступа к работающим
конфигам, поэтому триггер — `onEnable()` при следующем рестарте. Это покрывает
и апдейтер, и ручную замену JAR. Команда `/chrdk config diff` не добавлялась:
отчёт идёт в лог (`[config-schema] …`) с перечнем добавленных ключей,
переименований, удалений и именем backup'а.

## 4. Что проверяют тесты

`ConfigSchemaEngineTest` (8 JUnit-тестов, движок не требует сервера):

1. новый раздел добавляется вместе с комментариями, владельческие значения и
   комментарии сохранены;
2. повторный запуск идемпотентен и не возвращает удалённый владельцем ключ;
3. новый ключ внутри существующей секции вставляется в её конец;
4. карта миграции `rename`/`remove` сохраняет владельческое значение;
5. файл новее сборки не откатывается;
6. маркер `messages.yml` — комментарий, верхняя секция остаётся одна
   (совместимость с `Messages.flatten`);
7. шаг отступа владельца (4 пробела) сохраняется при вставке нового раздела;
8. битый YAML владельца остаётся нетронутым.

## 5. Границы и что не сделано

- Нет нового тега, prerelease, ZIP, правки `Latest`, TradeMC, соц. новостей,
  PR/merge в `main`, production, RCON, живого smoke и CHRDK_Live.
- `API_VERSION` не поднимался: `ConfigUpgrader` — внутренний класс ядра, а не
  контракт публичного API.
- `plugin.yml`, `messages_<locale>.yml`, конфиги в `docs/` и данные `*.json`
  не затрагиваются.
- Полная перестройка YAML, миграция **между** секциями (`rename` с переносом в
  другую секцию) и автоматическое выведение версии из diff эталона не
  реализованы — это осознанные ограничения первой версии.
- `docs/STAGING-SMOKE-1.5.2-rc.2.md` остаётся бумажным чек-листом: в
  песочнице нет JVM, Minecraft-сервера и клиента.
