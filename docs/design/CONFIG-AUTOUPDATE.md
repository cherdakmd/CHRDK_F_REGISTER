# Автоматическое обновление конфигов ядра и аддонов — аудит и варианты

**Статус:** проект на будущее, не реализация. Дата: 6 ноября 2026 года.
**Реализация не начата:** ни один исходник, `build.gradle`, `plugin.yml`,
конфиг, вики-страница или релиз для этой задачи не менялись. Документ
фиксирует пожелание владельца «было бы славно, если бы все конфиги
обновлялись автоматически с обновлением ядра и аддонов» и развилки, которые
надо решить до написания кода.
**Связанные материалы:** `docs/releases/1.5.2-rc.2.md` (п. 3 «Переход и
откат» — новые ключи сейчас читаются из дефолтов),
`docs/STAGING-SMOKE-1.5.2-rc.2.md` (п. 2.8 проверяет конфиги на staging),
`src/main/java/ru/cherdakmd/chrdkregister/Messages.java`,
`PresentationMigration.java`, `api/EconomyTariffMigration.java`,

## 1. Аудит: как устроено сейчас

| Что | Как работает | Следствие |
| --- | --- | --- |
| `config.yml` (Core + 22 аддона) | `saveDefaultConfig()` в `onEnable()` каждого плагина: файл создаётся **только если его ещё нет** | Существующий файл никогда не дополняется новыми ключами |
| Чтение новых ключей | Код везде указывает дефолт: `cfg.getBoolean("prestige.enabled", true)`, `cfg.getDouble("diamonds.base-chance", 0.01)` | Механика работает, но владелец **не видит** новый ключ в своём файле и не может его поправить, не дописав руками |
| `messages.yml` | `Messages.load/from/fromChecked` объединяет дефолты из ресурса JAR с оверрайдами из файла владельца **в памяти** | Новые тексты подхватываются автоматически; файл владельца не перезаписывается. Уже лучше, чем `config.yml` |
| Точечные миграции Core | `PresentationMigration` (меню, автосообщения, таб, каталог), `PremiumPresentationMigration`, `EconomyTariffMigration` | Обновляют **только конкретные стоковые секции** и только Core; сравнивают с 20+ снимками прошлых релизов, делают backup и атомарную запись |
| `PluginUpdateService` | Скачивает релиз, проверяет `plugin.yml`, складывает **JAR** в `plugins/update/`, делает backup JAR + `manifest.json` | Конфиги не трогает вообще; новый JAR начинает работать после рестарта |
| Версионирование конфигов | Маркера `config-version` / схемы нет | Нельзя отличить «уже обновляли» от «ещё нет», нельзя безопасно мигрировать переименования |
| Политика релизов | «Новые ключи отсутствуют в старом конфиге и читаются из значений по умолчанию; владельческие правки не перезаписываются» | Осознанный выбор в пользу безопасности, но он же и есть источник боли |

**Формулировка проблемы.** Обновление проходит незаметно для механики, но
«слепое» для администратора: после rc.2 в `skills/config.yml` не появились
`prestige.*`, `diamonds.*`, `excluded-materials`, хотя они уже работают. То же
для `anvil.*` в rc.1. Владелец узнаёт о новых ключах только из заметок.

## 2. Инварианты, которые нельзя нарушать

1. **Владельческие значения не перезаписываются.** Ни при обновлении, ни при
   reload. Стоковый текст меняется только если он точно совпадает с известным
   стоковым снимком (как в `PresentationMigration`).
2. **Комментарии и форматирование файла сохраняются.** `YamlConfiguration.save()`
   их **уничтожает** и переформатирует весь YAML — это главная техническая
   ловушка. В конфигах проекта много поясняющих комментариев; потеря недопустима.
3. **Backup до любой записи**, атомарная замена через temp-файл (прецедент —
   `PresentationMigration.apply`).
4. **Идемпотентность:** повторный старт не меняет файл и не плодит backup'ы.
5. **Не трогать данные.** Только `config.yml`/`messages.yml`, не `*.json`,
   `playerdata`, миры, банковские квитанции.
6. **Отчёт:** в лог и/или команду — что добавлено, что пропущено, где backup.
7. **Откат:** владелец может вернуть файл из backup, не останавливая всё
   обновление целиком.

## 3. Триггер

Обновление JAR через `PluginUpdateService` кладёт файлы в `plugins/update/` и
**не имеет доступа к работающим конфигам**. Поэтому естественный триггер —
`onEnable()` каждого плагина при следующем рестарте, сразу после
`saveDefaultConfig()` и до чтения конфига. Это автоматически покрывает и
обновление через апдейтер, и ручную замену JAR. Альтернатива — отдельная
команда `/chrdk config upgrade` (не «автоматически», но предсказуемее).

## 4. Варианты решения

### A. Аддитивный merge прямо в `config.yml` *(рекомендую как цель)*

Общий класс в Core (например `ConfigUpgrader.merge(JavaPlugin)`), который:
читает эталонный `config.yml` из ресурса JAR → читает файл владельца →
находит **только отсутствующие** ключи → дописывает их с дефолтами → backup →
атомарная запись → лог. Вызывается из `onEnable()` всех 23 плагинов.

- **Плюсы:** ровно то, что пожелал владелец; один механизм на все модули;
  владельческие значения не трогаются; работает и при ручной замене JAR.
- **Минусы:** `YamlConfiguration.save()` теряет комментарии. Значит нужен не
  «пересохранить», а **текстовое дополнение** новых секций в конец файла с
  сохранением исходного текста, либо собственный YAML-writer с комментариями.
- **Объём:** 1 новый класс в Core + 23 вызова + тесты на «старое значение
  сохранено, новый ключ добавлен, комментарии целы, повторный старт ничего не
  меняет» + freshness вики + CI.

### B. Отдельный файл дополнений *(самый безопасный первый шаг)*

Не трогать `config.yml` вообще. При старте писать
`config-new-<version>.yml` со списком новых ключей и дефолтами, плюс отчёт в
лог и команду `/chrdk config diff`.

- **Плюсы:** нулевой риск для владельческого файла и комментариев; легко
  откатить (удалить один файл); тривиальные тесты.
- **Минусы:** владельцу всё равно надо перенести ключи руками — «автоматически»
  только в смысле «автоматически показали, что появилось».

### C. Полная схема версий конфигов

Добавить `config-version: N` в каждый `config.yml`, карту миграций
`N → N+1` (добавление, переименование, удаление устаревших ключей), запуск по
маркеру, backup и отчёт.

- **Плюсы:** единственный вариант, который умеет **переименовывать** и
  вычищать мёртвые ключи; идемпотентен по маркеру.
- **Минусы:** самый большой объём; для 23 модулей нужна дисциплина ведения
  карт в каждом релизе; ошибка в карте может поправить владельческое значение.

### D. Только `messages.yml` на диск

Расширить уже работающий in-memory merge: при желании синхронизировать и файл
на диске. Отдельная задача, к `config.yml` отношения не имеет.

**Комбинация, которая выглядит разумной:** B как первый безопасный шаг → A с
текстовым сохранением комментариев как основной механизм → C только если
когда-нибудь понадобятся переименования. D — по отдельному решению.

## 5. Открытые вопросы для владельца

1. **Переписывать ли файл?** Если да — согласны ли на потерю комментариев, или
   обязательно текстовое дополнение (вариант A с оговоркой)?
2. **`messages.yml`** тоже «все конфиги»? Сейчас новые тексты уже подхватываются
   в памяти; нужно ли их физически дописывать в файл?
3. **Устаревшие ключи:** оставлять навсегда или когда-нибудь вычищать (вариант C)?
4. **Отчёт:** только лог или команда `/chrdk config diff` / `upgrade`?
5. **Граница обновления:** только `config.yml` каждого модуля, или ещё
   `plugin.yml`, `messages_<locale>.yml`, конфиги в `docs/`?
6. **Когда:** правки в активной ветке **после** `v1.5.2-rc.2` (тег и ассеты
   не переписываются) или следующим релизом?
7. **`API_VERSION`:** если `ConfigUpgrader` станет частью публичного API Core,
   нужен ли bump с 42 — отдельное решение.

## 6. Оценка объёма и рисков

| Вариант | Файлов | Тестов | Риск для владельческих данных |
| --- | --- | --- | --- |
| B | ~3 (Core + команда/отчёт + тест) | ~6 | Нулевой |
| A | ~25 (Core + 23 вызова + тесты + вики) | ~12 | Низкий при текстовом дополнении, **высокий при `YamlConfiguration.save()`** |
| C | ~30+ (карты миграций на модуль) | ~20 | Средний |
| D | ~2 | ~4 | Низкий |

Любая реализация потребует: freshness для страниц с `review: [core, …]`,
`check_messages`, `check_retired_addons`, дерево YAML, tree-sitter Java,
Gradle-сборку/JUnit на Java 25 в CI и явной записи в заметках релиза о том,
что конфиг теперь обновляется автоматически (это меняет инструкцию «сверьте
авторские конфиги» в `docs/releases/update-memo.txt`).

**Пока не сделано ничего, кроме этого аудита.** Тег `v1.5.2-rc.2`, его ассеты,
`Latest = v1.5.1`, TradeMC, production, RCON и живой smoke не менялись.
