# CHRDK_F_REGISTER — 12 предложений по развитию

Документ описывает **12 нововведений и улучшений** плагина (исходная версия 1.2.0, Purpur 1.21.11 / Java 21).
Для каждого пункта указано, что было не так (со ссылками на файлы и строки исходной версии), что
предлагается сделать, какие классы и ключи `config.yml` появятся, а также приоритет и трудоёмкость.

> **Статус реализации (ветка `arena/a713a830-chrdk-f-register`, версия 1.3.0):** все 12 пунктов реализованы и
> собираются в GitHub Actions (сборка + тесты, включая тест полноты `messages.yml`).
> Сводка по файлам — в `README.md`, описание файла текстов — в разделе «Тексты и локализация» ниже.

Обозначения:

- **Приоритет**: `P1` — делать первым (деньги, безопасность, производительность), `P2` — важное улучшение, `P3` — «когда будет время».
- **Объём**: `S` — до 1 дня, `M` — 2–3 дня, `L` — неделя и больше.

## 1. Вход через нативные диалоги и маскирование паролей в логах

**Проблема.** Пароль передаётся аргументом команды: `/login <пароль>`
(`RegisterCommandHandler.handleLogin`, `handleRegister`, `handleChangePassword`). Следствия:

- команда игрока целиком попадает в консоль и `logs/latest.log` в виде
  `«<ник> issued server command: /login пароль»` — это поведение Spigot/Paper (`spigot.yml → commands.log: true`),
  поэтому пароль остаётся на диске в открытом виде;
- пароль виден в чате игрока (скроллбэк), в записях и стримах;
- текст команды видят все плагины/прокси/античиты, слушающие `PlayerCommandPreprocessEvent`;
- пароль дополнительно проходит через обычный путь обработки команд, где его легко залогировать случайно.

**Предложение.**

1. Перевести ввод секретов на **Paper Dialog API** (доступен с 1.21.6, поддерживается 1.21.11):
   `DialogInput.text` + `PlayerCustomClickEvent` / `DialogResponseView`. Игрок нажимает кнопку
   «Войти» в чате → открывается диалог с полем ввода → значение уходит прямо на сервер и **не попадает
   в чат и логи**. Отдельные диалоги: вход, регистрация, смена пароля, ввод кода 2FA, отключение 2FA.
2. Оставить команды как fallback (для клиентов/версий без диалогов) и пометить их в README как «устаревший способ».
3. Добавить **маскирование в логах**: log4j2-фильтр (или перехват `PlayerCommandPreprocessEvent`
   на `MONITOR` + собственная запись «masked» строки) для команд `login/register/changepassword/2fa`,
   чтобы в `latest.log` попадало `/login ********`. Немедленная мера «сегодня» —
   `spigot.yml → commands.log: false` (минус: перестают логироваться все команды игроков, включая
   подозрительные; применять осознанно).
4. Пока диалоги не внедрены — добавить в README явное предупреждение администратору
   («пароли игроков попадают в `logs/latest.log`»).

```yaml
auth:
  # Предпочитать диалоги вместо команд (Paper 1.21.6+)
  dialogs: true
  # Как показывать приглашение: dialog | command
  prompt-style: dialog
  # Маскировать аргументы команд авторизации в консоли и logs/latest.log
  mask-commands-in-logs: true
```

**Что менять.** Новый класс `AuthDialogs` (`ru.cherdakmd.chrdkregister.dialog`), слушатель
`PlayerCustomClickEvent`; `RegisterCommandHandler` — приглашения вместо «введите команду»;
`AccessManager` — публичные методы уже есть (`handleLoginCommand`, `handleRegisterCommand`,
`handleTwoFactorLoginCode`), их повторно используем из диалогов; `plugin.yml` — ничего.

**Эффект.** Пароли перестают утекать в логи и чат; вход становится в разы понятнее новым игрокам
(кнопка вместо запоминания синтаксиса). **Проверка:** `/login` не появляется целиком в `latest.log`.

## 2. Настоящий антибрутфорс: счётчики на диске, лимиты по IP, задержка, алерты

**Проблема.** Счётчик неудачных попыток живёт в памяти и **сбрасывается при каждом входе игрока**:

- `AccessManager.java:217-218` — `failedLoginAttempts.remove(uuid)` и `failedTotpAttempts.remove(uuid)` в `onPlayerJoin`;
- `AccessManager.java:352-356` — после `maxLoginAttempts` игрока кикают, он заходит снова и получает новые 5 попыток.

Также нет ограничения по IP: один и тот же адрес может перебирать пароли к сотне аккаунтов, а
`session-minutes` и напоминания не мешают автоматизации.

**Предложение.**

- Хранить счётчики **в `data.json`** (по аккаунту и по IP) с окном времени и «до какого момента блокировка».
- **Экспоненциальная задержка** подбора: 1-я ошибка — 0 сек, 5-я — 5 сек, 10-я — 30 сек, 20-я — 5 мин (`auth.backoff`).
- Отдельные лимиты: `per-account` (например, 8/10 мин), `per-ip` (например, 15/10 мин на все аккаунты).
- При превышении — временный **бан IP** через `Bukkit.getBanList(BanList.Type.IP)` на N минут (с записью причины).
- Уведомление онлайн-администраторов и вебхук (см. п. 9) при всплеске неудач, с указанием ника и IP.
- Сбрасывать счётчик **только при успешном входе**, а не при подключении.

```yaml
auth:
  brute-force:
    backoff-seconds: [0, 0, 1, 2, 5, 10, 30, 60, 120, 300]   # по номеру неудачи
    account-max-attempts: 8
    account-window-minutes: 10
    per-ip-max-attempts: 15
    per-ip-window-minutes: 10
    temp-ip-ban-minutes: 15
    notify-admins: true
```

**Что менять.** `RegistrationStore` (новая структура `attempts` + миграция схемы из п. 8),
`AccessManager` (`handleLoginCommand`, `handleTwoFactorLoginCode`), новый `BanService` (или частный
метод в `AccessManager`), `PlayerRestrictionListener` — не блокировать вход по бану лишний раз.

**Эффект.** Перебор пароля становится экономически бессмысленным, а атака видна администрации
в реальном времени. **Проверка:** unit-тест «25 неудачных попыток после перезахода → вход заблокирован».

## 3. Сессия по IP: не обходит 2FA, привязка к UUID, `/logout`, уведомления

**Проблема.** «Сессия по IP» (`auth.session-minutes`, по умолчанию 30) фактически отключает вторую
фактор для всех, у кого есть 2FA:

- `AccessManager.java:237-247` — при совпадении IP игрок сразу получает `AUTHENTICATED`, код TOTP не спрашивается;
- `RegistrationStore.hasValidIpSession` (`RegistrationStore.java:274-296`) сверяет **только ник и IP**,
  без UUID: любой, кто окажется за тем же IP в течение 30 минут (дом, VPN, NAT мобильного оператора,
  интернет-кафе), входит на аккаунт вообще без пароля;
- нет команды «выйти», нельзя отозвать сессию вручную, игрок не видит, что вошёл «по сессии».

**Предложение.**

- Новый параметр `auth.session-skips-2fa` (по умолчанию `false`): при включённой 2FA IP-сессия
  пропускает только пароль, но **не** код. Для «своих» случаев админ может включить осознанно.
- Сверять сессию с UUID (`account.uuid`), добавить `auth.session-require-same-uuid: true`.
- Показывать при входе по сессии отдельное сообщение и звук, а также «Сессия активна до …».
- Команды: `/logout` (сброс своей IP-сессии и выход в NO_PASS→NEEDS_LOGIN), `/session` (показать активные
  сессии аккаунта и завершить их), админская `/pass sessions <ник>` + `/pass logoutall <ник>`.
- Ограничить число одновременных сессий и уведомлять игрока о входе по сессии с нового адреса.

```yaml
auth:
  session-minutes: 30
  session-skips-2fa: false
  session-require-same-uuid: true
  session-notify: true
  max-sessions-per-account: 2
```

**Что менять.** `RegistrationStore` (`hasValidIpSession`, `clearSession` уже есть — добавить список
сессий), `AccessManager.onPlayerJoin`, `RegisterCommandHandler` (`logout`, `session`, `pass sessions`),
`PlayerRestrictionListener` (разрешить `/logout` на этапе `NEEDS_LOGIN`/`AUTHENTICATED`).

**Эффект.** 2FA снова защищает (сейчас — только при отсутствии IP-сессии), пропадает дыра
«общий IP = общий аккаунт». **Объём малый**, это самая дешёвая правка безопасности в списке.

## 4. Политика паролей и защита от «общих» аккаунтов

**Проблема.** Сейчас проверяется только длина (`auth.min-password-length: 6`,
`AccessManager.handleRegisterCommand` / `handleChangePasswordCommand`). Пароли вроде `123456`,
`qwerty`, `никнейм` принимаются. Нет защиты от мультиаккаунтов — при платной проходке
один игрок делит аккаунт с друзьями, оплата идёт за одного, играют пять.

**Предложение.**

- Минимальная длина по умолчанию **8**, запрет на совпадение с ником (в любом регистре), запрет
  пароля из встроенного словаря частых (топ-1000) и проверка на «монотонность» (`12345678`, `aaaaaaaa`).
- Индикатор надёжности при регистрации (Weak/Medium/Strong) + подсказка, что улучшить.
- Запрет одинакового пароля между аккаунтами: при регистрации проверять пароль-кандидат по хэшам
  аккаунтов, заходивших с того же IP (ограничить список последними N аккаунтами, чтобы не тратить CPU),
  и предупреждать, что пароль уже используется другим аккаунтом — без раскрытия, каким именно.
- Флаг мультиаккаунта: если с одного IP успешно авторизовались N разных аккаунтов с активными
  проходками — записать в аудит-лог (п. 9) и уведомить админов: `anti-multialt.notify-admins`.
- Опционально — жёсткий режим `anti-multialt.mode: deny|notify` (deny запрещает вход новому аккаунту с общего IP).

```yaml
auth:
  min-password-length: 8
  reject-common-passwords: true
  reject-nickname-as-password: true
  password-strength-hint: true
anti-multialt:
  enabled: true
  mode: notify            # notify | deny
  max-accounts-per-ip: 3
  count-only-active-pass: true
```

**Что менять.** Новый `PasswordPolicy` (чистая логика — легко покрыть тестами рядом с `PasswordHasher`),
`PluginConfig`, `AccessManager`, `RegistrationStore` (индекс IP→аккаунты по `lastAuthIp`).

**Эффект.** Пароли становятся реально защитными, а «экономика проходок» — честной.

## 5. Ни один донат не теряется: очередь `pending`, код сопоставления, `/pass approve`

**Проблема.** Самое дорогое место плагина. Сопоставление доната с игроком делается по полю
«Ваше имя» (`DonatePayClient` → `vars.name`), а результат ошибки — только строчка в логе:

- `AccessManager.processTransaction`: при `strict-case-match: true` и несовпадении регистра
  (`RegistrationStore.grantPassFromDonation` вернул `empty`) донат **молча игнорируется**, но в
  `pollDonationsSafely` всё равно вызывается `store.markDonationProcessed(id)` — деньги пришли, проходки нет,
  админ об этом не узнает;
- нет списка «нераспознанных» платежей и ручного разбора: `/pass add <ник>` выдаёт проходку, но
  связать это с конкретной транзакцией невозможно;
- нет журнала всех транзакций (включая суммы ниже минимума) — при разборе спора с игроком смотреть нечего;
- при опечатке в нике («Stevee» вместо «Steve») деньги теряются: автоматики на «похожее имя» нет.

**Предложение.**

1. **Журнал транзакций** `donations.json`: каждый платёж из API сохраняется со статусом
   `granted | pending_name | pending_amount | pending_review | rejected`, суммой, именем донатера, ID, датой.
2. **Очередь `pending`**: всё, что не удалось выдать автоматически (несовпадение по регистру,
   сумма ниже минимума, ник не похож на игровой, донат вне окна), попадает туда и **не считается обработанным
   как «молча потеряно»**.
3. **Сопоставление с подтверждением**:
   - администратор видит `/pass pending` (список с суммами и временем) и решает
     `/pass approve <id>` (выдать вручную, с записью в аудит) или `/pass reject <id>`;
   - нечёткое сопоставление по нику (нормализация регистра, `_`, RU/EN-раскладка, расстояние Левенштейна ≤ 1)
     формирует **подсказку** рядом с платежом, но не решает автоматически;
   - если игрок онлайн — кнопка «подтвердить, что это мой платёж» (`/pass claim <id>`), после чего выдача
     срабатывает автоматически, а админ получает уведомление «выдано автоматически по подтверждению игрока».
4. **Код платежа (опция)**: просить указывать в имени донатера `Ник 4821` (случайные 4 цифры, выдаются
   игроку и показаны в подсказке). Тогда сопоставление детерминированное, без опоры на регистр букв.
   Требует, чтобы DonatePay позволял передать/отобразить такой текст в поле имени — проверить на
   тестовом платеже перед включением; до этого опция остаётся выключенной и работает вариант 3.
5. Массовые операции: `/pass pending resend` (повторная попытка автосопоставления) — если игрок зарегистрировался позже.

```yaml
donatepay:
  unmatched-donations: review      # review | ignore
  fuzzy-match: true
  payment-code: false              # подсказывать "Ник 4821" в имени донатера
  code-digits: 4
  journal-file: donations.json
  keep-days: 365
```

**Что менять.** `DonatePayClient` (без изменений API, только полнота данных), `RegistrationStore`
(журнал + методы), `AccessManager.pollDonationsSafely` / `processTransaction`, `RegisterCommandHandler`
(`/pass pending|approve|reject|claim`), README (инструкция покупателю).

**Эффект.** Ноль «тихих» потерь и понятный разбор: админ всегда может сказать, что произошло с деньгами.
Это ключевой пункт для проекта, который живёт на донатах. *(Докручено в 1.4.23: повторная оплата при
активной проходке складывается с остатком — автотест `DonationStackingTest`; донаты с платёжным кодом
(«Ник 1234») матчатся автоматически и принимаются в `/pass claim`; тестовые команды `/pass testpay
<ник> [сумма]` (полный цикл без API) и `/pass recheck` (внеочередной опрос DonatePay).)*

## 6. Тарифы, подарки, ручная выдача на произвольный срок

**Проблема.** Единственный тариф — «от 150 ₽ → 30 дней» (`donatepay.minimum-rubles`, `pass.grant-days`),
одинаковый для авто- и ручной выдачи. Нет скидок за длинный срок, нет продления на 3/12 месяцев,
нельзя подарить проходку другу, `/pass add <ник>` не принимает срок.

**Предложение.**

- Лестница тарифов: сумма → длительность, с валидацией «не хуже, чем за 1 месяц»:
  ```yaml
  pass:
    tiers:
      - { amount: 150,  days: 30,  label: "1 месяц" }
      - { amount: 400,  days: 90,  label: "3 месяца" }   # выгоднее на 11%
      - { amount: 1400, days: 365, label: "Год" }
    fallback-days: 30            # если сумма больше тарифа, но не дотягивает до следующего
    extend-from-max: true        # продление от максимума(now, passUntil) — уже так и работает
  ```
- Показ игроку таблицы тарифов в `/pass` и в сообщении без проходки, с указанием, сколько дней даст каждая сумма.
- `/pass add <ник> <дни> [причина]` — произвольный срок вручную (аргумент по умолчанию — `pass.grant-days`).
- `/pass gift <ник> <дни>` — подарить проходку; для автоподарков — связка с п. 5 (код платежа и
  подтверждение получателя). Запись в аудит: кто, кому, сколько, на сколько.
- `/pass info` — «сколько ещё действует», «когда последний донат», «сколько всего оплачено» (из журнала п. 5).

**Что менять.** `PluginConfig` (парсинг `pass.tiers`), `RegistrationStore.grantPassManual` (срок уже
параметром — нужен только новый путь вызова), `AccessManager.qualifiesForPass`/`processTransaction`
(выбор дней по сумме), `RegisterCommandHandler`.

**Эффект.** Рост среднего чека (скидки за длинный период — проверенный приём) и гибкость для саппорта.

## 7. Предупреждения об окончании проходки и продление без перезахода

**Проблема.** Проходка заканчивается молча: игрок узнаёт об этом в момент, когда уже заблокирован
(`AccessManager.tickOnlinePlayers` → «Срок вашей месячной проходки истёк!»). Это худший момент для
конверсии: игрок уже раздражён, а не «почти готов продлить».

**Предложение.**

- Настраиваемые напоминания до окончания: за 7 дней, 3 дня, 1 день и 1 час — с остатком срока и
  кликабельной ссылкой на оплату.
- За последний час — `BossBar` с обратным отсчётом (или ActionBar), чтобы продление было «на виду».
- Уведомление после продления: «Проходка продлена на X дней, действует до …» — уже есть, дополнить
  суммой и источником.
- Главное: **продление до истечения не должно ронять сессию** — если игрок оплатил, пока блокировка
  ещё не сработала, он даже не должен увидеть экран оплаты (сейчас корректно, но стоит закрепить тестом).
- В `/pass` — «Продлить» кнопкой, открывающей страницу оплаты.

```yaml
pass:
  expiry-warnings-minutes: [10080, 4320, 1440, 60]   # 7д, 3д, 1д, 1ч
  expiry-bossbar: true
  expiry-warning-sound: true
```

**Что менять.** `AccessManager` — новый блок в `tickOnlinePlayers` + состояние «что уже показали»
в памяти (и в `data.json`, чтобы не повторять после рестарта), `config.yml`, `README.md`.

**Эффект.** Продления происходят до блокировки, а не после жалобы в Discord; меньше «мёртвых» окон.

## 8. Надёжное хранение: async-запись, бэкапы, версия схемы и миграции

**Проблема.** `data.json` — единственный источник правды и переписывается **целиком, синхронно, в основном
потоке**:

- `RegistrationStore.recordPlayerSeen` вызывает `save()` на каждом входе (`RegistrationStore.java:45-55`);
- `touchSession` (`RegistrationStore.java:298-312`) сохраняет файл на каждый вход/выход и на каждую смену права;
- `addIgnoredPlayer`/`removeIgnoredPlayer` — тоже `save()`;
- все методы `synchronized`, а вызываются они из main-потока (`AccessManager.onPlayerJoin`) — при тысячах
  аккаунтов это заметные лаги на входе и «пила» MSPT при массовом заходе;
- бэкап только один — `data.json.corrupt-<millis>` при ошибке чтения; плановых бэкапов нет;
- в файле нет версии схемы, значит любое изменение структуры (см. пп. 2, 4, 5) невозможно мигрировать безопасно.

**Предложение.**

1. **Отложенная запись**: пометка «dirty» + запись раз в N секунд (например, 10) и принудительно при
   выключении/`/pass reload`; запись в отдельном потоке (`Bukkit.getScheduler().runTaskAsynchronously`),
   атомарный `ATOMIC_MOVE` уже используется — оставить.
2. **Ротация бэкапов**: `backups/data-YYYYMMDD-HHmmss.json`, хранить N последних (по умолчанию 14),
   сжатие gzip; команда `/pass backup [create|list|restore <файл>]`.
3. **Версия схемы**: поле `"version": 3` в корне файла и цепочка миграций `v1→v2→v3`; при загрузке —
   авто-миграция с предварительным бэкапом. Юнит-тесты на каждую миграцию (у проекта уже есть
   `RegisterPluginTest` с `@TempDir` — паттерн готов).
4. **Страж целостности**: `sha256` в конце файла или sidecar `.sha256`; при несовпадении — отказ от
   загрузки и восстановление из последнего бэкапа с громким алертом.
5. `/pass doctor` (п. 10) проверяет доступность каталога, права на файл, размер и валидность JSON.

```yaml
storage:
  save-debounce-seconds: 10
  write-async: true
  backup-count: 14
  backup-on-start: true
```

**Что менять.** `RegistrationStore` (единственный класс, но капитально), `RegisterPlugin.onDisable`
(гарантированный flush), `RegisterCommandHandler` (`/pass backup`).

**Эффект.** Исчезают лаги на входе и риск потерять всё из-за одного сбойного файла; появляется база
для любых будущих изменений данных.

## 9. Аудит-лог (JSONL) и уведомления в Discord

**Проблема.** Все значимые события пишутся только в `latest.log` и в чат, то есть теряются при ротации
логов и недоступны для разбора. Нет уведомлений администрации о важном (новый донат, всплеск неудачных
входов, сброс 2FA, отзыв проходки). При спорах («я оплатил», «меня взломали», «админ снял проходку»)
доказательной базы нет.

**Предложение.**

- **Аудит-лог** `audit/audit-YYYY-MM-DD.jsonl`: строка на событие с полями `time`, `event`, `actor`,
  `target`, `ip`, `details`. События: `pass.grant.donatepay`, `pass.grant.manual`, `pass.revoke`,
  `pass.expire`, `password.change`, `password.reset`, `totp.enable`, `totp.disable`, `totp.reset`,
  `login.success`, `login.fail`, `bruteforce.alert`, `session.restore`, `chat.mute`, `chat.broadcast`, `config.reload`.
- Чтение: `/pass audit [ник] [страница]` — последние N событий с фильтром, у права `chrdkregister.admin.audit`.
- **Discord-вебхук** (обычный `HttpClient`, без внешних зависимостей): уведомления о донатах и выдачах,
  брутфорсе, сбросах 2FA/пароля, отзывах проходки, ошибках DonatePay (уже есть троттлинг-предупреждение —
  добавить туда вебхук). Формат — embed, цвет по типу события.
- Ключи выключены по умолчанию: ничего не отправляется без явного `webhook-url`.

```yaml
audit:
  enabled: true
  keep-days: 180
  log-logins: true
notifications:
  discord-webhook-url: ""
  events: [pass.granted, pass.revoked, bruteforce.alert, totp.reset, donatepay.error]
  mentions: ["<@&ROLE_ID>"]     # необязательно
```

**Что менять.** Новый `AuditLog` (запись + ротация файлов) и `NotificationService` (вебхуки, ретраи,
троттлинг), вызовы из `AccessManager`, `ChatService`, `RegisterCommandHandler`.

**Эффект.** Полная история для разбора конфликтов, мгновенная реакция администрации на инциденты.

## 10. `/pass stats`, `/pass doctor`, bStats, опциональный `/metrics`

**Проблема.** `/pass status` показывает только счётчики «сейчас» (активные проходки, зарегистрированные
пароли, включённая 2FA). Нет истории: сколько выдано за день/неделю, сколько денег пришло, какая конверсия
«зашёл → оплатил», сколько платежей не распознано. Нет самопроверки конфигурации: об ошибках в токене/URL
админ узнаёт по логам.

**Предложение.**

- `/pass stats` — выручка и выдачи за сегодня/7 дней/30 дней (из журнала п. 5 и аудита п. 9),
  конверсия `первый вход → активная проходка`, топ по суммам, счётчик `pending` платежей.
- `/pass doctor` — проверки: доступен ли DonatePay (пробный запрос), валиден ли `payment-url`,
  права на `data.json`, корректны ли ключи (диапазоны `min/max`, `session-minutes`, `window-steps`),
  пересекаются ли команды чата с другими плагинами, включён ли 2FA, не равен ли `grant-days` нулю и т. п.
  Вывод — таблица «ок/warning/error» с советами.
- **bStats** (библиотека `bstats-bukkit` + числовой ID плагина с bstats.org) — анонимная статистика:
  версия, число аккаунтов, доля 2FA. Наружу уходят только агрегаты, ничего из `data.json`.
- **Опциональный HTTP `/metrics`** в формате Prometheus (`passes_active`, `donations_pending`,
  `logins_failed_total`, `donatepay_api_failures_total`), выключен по умолчанию, доступ только с localhost
  или по токену.

```yaml
metrics:
  bstats: true
  prometheus:
    enabled: false
    host: 127.0.0.1
    port: 9940
    token: ""
```

**Что менять.** Новый `StatsService` (агрегация поверх журналов), `DoctorCommand`, `MetricsEndpoint`
(лёгкий `com.sun.net.httpserver.HttpServer`, без зависимостей).

**Эффект.** Видно, что приносит деньги и где узкие места; конфигурационные ошибки ловятся до жалоб игроков.

## 11. Модерация чата: mute, slow-mode, фильтр слов, лог чата

**Проблема.** Встроенный чат имеет антиспам «на игрока» (`ChatService.onAsyncChat`: задержка, длина,
КАПС, дубли), но полностью отсутствует модерация: нельзя замутить нарушителя, нет фильтра
нецензурной лексики и рекламы, нет режима «медленный чат» для глобального канала, нет истории чата
для разбора жалоб. Упоминания `@ник` рассылаются без ограничения — одно сообщение может «дёрнуть»
весь сервер (`ChatService.notifyMentions`).

**Предложение.**

- `/mute <ник> <10m|2h|1d> [причина]`, `/unmute <ник>`, `/mutes` — блокировка чата и ЛС, сохраняется
  в `data.json`, переживает перезаход. Право `chrdkregister.chat.mute`.
- **Фильтр**: список запрещённых слов/регулярных выражений с заменой (`***`) или блокировкой сообщения;
  отдельно — фильтр ссылок/IP/`discord.gg` с белым списком; уведомление админам о срабатывании.
- **Slow-mode**: `/chat slow <секунды|off>` — общий для глобального канала (расширение
  существующего `cooldown-seconds`, который действует лишь персонально).
- **Лог чата**: `logs/chat/chat-YYYY-MM-DD.log` (или JSONL) со всеми каналами и ЛС + `/chat history <ник> [N]`
  (право `chrdkregister.chat.history`), `/chat history ip <адрес>` — для разбора.
- **Лимит упоминаний** в одном сообщении (`chat.max-mentions`, по умолчанию 3), защита от
  «упоминание всего сервера»; уведомления об упоминаниях — с троттлингом на получателя.
- Расширение защиты от флуда на группу аккаунтов: при N одинаковых сообщениях от разных аккаунтов за
  короткое окно — «заморозка» глобального канала на 10 секунд + алерт в аудит (п. 9).

```yaml
chat:
  max-mentions: 3
  filter:
    enabled: true
    mode: replace            # replace | block
    words: ["слово1", "слово2"]
    regex: ["(?i)https?://", "(?i)discord\\.gg/"]
    whitelist: ["youtube.com/@myserver"]
    notify-admins: true
  slow-mode-seconds: 0
  chat-log:
    enabled: true
    keep-days: 90
    include-private: true
```

**Что менять.** `ChatService` (фильтр, slow-mode, лимит упоминаний, логирование), `ChatConfig`,
`ChatCommandHandler` (`/mute`, `/unmute`, `/chat slow`, `/chat history`), `RegistrationStore` (муты),
`plugin.yml` (команды и права).

**Эффект.** Чат можно доверить модераторам без сторонних плагинов; на жалобы есть доказательства.

## 12. `messages.yml` + MiniMessage: убрать хардкод из кода

**Проблема.** Все тексты — жёстко в Java-коде, часто с константами, которые обязаны совпадать с
конфигом, но не совпадают:

- `PlayerRestrictionListener.java:117` — «приобретите проходку (**150₽** на DonatePay…)», хотя минимум
  задаётся в `donatepay.minimum-rubles`;
- `AccessManager` — «Стоимость проходки», подсказки, тайтлы, напоминания, вся переписка 2FA;
- `RegisterCommandHandler` — все справки и сообщения об ошибках;
- часовой пояс «МСК» зашит в `AccessManager.DATE_FORMAT` (строки 41–42) — на сервере с другим поясом
  время в `/pass check` будет вводить в заблуждение;
- форматирование — `LegacyComponentSerializer.legacyAmpersand()` (`ChatService.legacy`), то есть
  градиенты, hover с несколькими строками и MiniMessage-теги недоступны.

**Предложение.**

- Файл `messages.yml` со всеми строками, поддержкой `%placeholders%` и наследованием значений по
  умолчанию (недостающие ключи добираются из ресурса плагина — при обновлении конфиг не ломается).
- **MiniMessage** вместо `&`-кодов (с обратной совместимостью: строки с `&` продолжают работать),
  поддержка `<gradient>`, `<hover>`, `<click>`, `<lang>`.
- Ключ `general.timezone` (по умолчанию `Europe/Moscow`) для всех дат.
- Проверка при `/pass reload`: неизвестные плейсхолдеры и ошибки формата MiniMessage — предупреждение админу.
- Тест `messages.yml` на полноту: набор ключей из ресурса == набор, который читает код (защита от
  «забыли добавить строку» при новом функционале).

```yaml
# messages.yml (фрагмент)
general:
  timezone: Europe/Moscow
  prefix: "<gray>[<gold>CHRDK</gold>]</gray> "
no-pass:
  chat: "<red>У вас нет активной проходки!</red> <gray>Оплата: </gray><click:open_url:'%payment_url%'><aqua>%price%₽</aqua></click>"
  title-subtitle: "<yellow>Донат %price%₽ на DonatePay (ник: %player%)</yellow>"
login:
  wrong-password: "<red>Неверный пароль! Осталось попыток: %attempts_left%</red>"
```

**Что менять.** Новый `Messages` (загрузка, дефолты, MiniMessage-рендер, плейсхолдеры), правки во всех
классах, где есть `Component.text("…")`: `AccessManager`, `RegisterCommandHandler`, `ChatService`,
`ChatCommandHandler`, `PlayerRestrictionListener`, `RegisterPlugin`.

**Эффект.** Сервер сам настраивает тексты и брендинг; исчезают расхождения вида «150₽» в коде против
конфига; открывается путь к мультиязычности (второй файл `messages_en.yml`).

**Как реализовано (1.3.0).**

- `src/main/resources/messages.yml` — 409 ключей, сгруппированных по разделам (`common`, `error`, `usage`,
  `restriction`, `password`, `register`, `login`, `two-factor`, `session`, `no-pass`, `pass`, `stats`,
  `account`, `donation`, `audit`, `backup`, `doctor`, `config`, `status`, `chat`, `mute`, `private-messages`,
  `socialspy`, `ignore`, `bruteforce`, `dialog`). В шапке — памятка по MiniMessage, `%подстановкам%`,
  экранированию и `/pass reload`.
- `Messages` — загрузка значений из JAR, наложение файла с диска, `%ключ%`-подстановки с экранированием,
  списки строк (`getList`/`sendList`) и разметка MiniMessage; `&`-коды конвертируются автоматически,
  поэтому старые форматы из `config.yml` продолжают работать.
- Недостающие в файле ключи берутся из ресурса плагина: обновление плагина не ломает уже настроенный
  `messages.yml` (в лог пишется, сколько ключей добрано из значений по умолчанию).
- `/pass reload` перечитывает `config.yml` и `messages.yml` и сообщает админу о проблемах: лишние ключи,
  незакрытые теги MiniMessage, потерянные подстановки (`Messages.validate()`).
- `general.locale` в `config.yml`: `ru` — файл `messages.yml`, другое значение — наложение
  `messages_<locale>.yml` поверх русских значений по умолчанию (заготовка под мультиязычность).
- `MessagesTest` — тест полноты: набор ключей в ресурсе сверяется с ключами, которые реально читает код
  (плюс проверка отрисовки MiniMessage, экранирования подстановок и фолбэка на значения по умолчанию).

## Приложение A. Быстрые победы (до одного дня)

1. `/logout` — сброс IP-сессии игроком (правки минимальны, `store.clearSession` уже есть).
2. Убрать хардкод «150₽» в `PlayerRestrictionListener.java:117` (подставлять `config.minimumDonationRubles()`).
3. `/pass add <ник> <дни>` — произвольный срок (метод `grantPassManual` уже принимает `durationMillis`).
4. Предупреждение в README: пароли из `/login` попадают в `logs/latest.log`; ротация логов 14+ дней.
5. `auth.kick-after-seconds` — кик незалогинившихся через N минут, чтобы освобождать слоты.
6. Ограничение напоминаний: не слать тайтл чаще, чем раз в N минут (сейчас тайтл при входе + чат каждые 15 с).
7. В `/pass check` показывать `lastAuthIp` (маскированно, `192.168.***.***`) и дату последнего входа. *(Реализовано в 1.3.0: строка «Последний вход» — `account.last-auth-*` в messages.yml.)*

## Приложение B. Крупные инициативы (за пределами списка)

- **MySQL/PostgreSQL + сеть серверов (Velocity/BungeeCord).** Единое хранилище вместо `data.json`,
  гейт на прокси: неаутентифицированного игрока вообще не пускать на игровые серверы
  (через `PluginMessage`/`pre-login`), авторизация на лобби/лимо-сервере. Это архитектурный шаг,
  который даёт сеть серверов и снимает половину задач по безопасности.
- **QR-код для 2FA.** Рендер `otpauth://` в виде карты (`MapView` + свои пиксели, без зависимостей
  или через ZXing) — привязка 2FA за один скан вместо ручного ввода 32 символов.
  *(Реализовано в 1.4.3: контекстная карта с личным QR при `/2fa setup` и по `/2fa qr`,
  встроенный генератор QR (Nayuki qrcodegen, MIT), настройка `totp.qr-map`.)*
- **GUI-меню `/pass`.** Инвентарь с иконками: «Оплатить», «Тарифы», «2FA», «Сменить пароль», «Сессия»,
  «Статистика» — вместо длинных текстовых справок. *(Реализовано в 1.4.5: `/pass menu` (алиас `/pass gui`),
  раскладка зависит от стадии игрока и прав, действия делегируются обычным командам,
  настройка `pass.gui-menu`.)*
- **Аддоны на API основного плагина.** Отдельные Bukkit-плагины с `depend: [CHRDK_F_REGISTER]`,
  использующие `ChrdkRegisterApi` (ServicesManager), события выдачи/отзыва/истечения проходок и
  завершения авторизации, а также мягкие привязки Vault/LuckPerms. *(Основа реализована в 1.4.6:
  `ru.cherdakmd.chrdkregister.api`, 4 события, `integrations.pass-group`, /pass doctor.)*
- **Аддон: магазин обмена ресурсов с динамическими ценами («алмазная валюта»).** Отдельный плагин
  поверх API 1.4.6. Валюта — все разновидности алмаза: `DIAMOND`, `DIAMOND_ORE`,
  `DEEPSLATE_DIAMOND_ORE`, `DIAMOND_BLOCK` (с авто-конверсией: 1 блок = 9 алмазов). Игрок продаёт
  ресурсы магазину за алмазы и покупает за них же; цены пересчитываются по спросу/предложению:
  индекс цены товара растёт при активных продажах магазина этого товара и падает при скупке
  по спросу/предложению. Доступ к магазину — только авторизованным
  (`PlayerAuthCompletedEvent` / `api.isAuthenticated`), тем самым экономика не используется
  ботами до входа. *(Реализовано в 1.4.7: subproject `diamond-shop` — отдельный плагин
  `chrdk-diamond-shop`, балансы и запасы в `shop-data.json`, цены по модели «запас/эталон» с
  `pricing.stock-recovery-per-hour`, витрина `/shop` в инвентаре, команды `/shopadmin`,
  Messages/MiniMessage ядра переиспользованы — это эталонный образец аддона.
  Докручено в 1.4.8: спред bid/ask, история цен со спарклайном, дневной лимит оборота,
  /shop sellall.)*
- **Аддон: общие цели сообщества.** Кооперативные волны целей с вкладом каждого
  игрока, награда пулом алмазов пропорционально вкладу, оффлайн-выдача.
  *(Реализовано в 1.4.17 по прямому запросу: subproject `common-goals` —
  `chrdk-common-goals`, `/goals` + `/goalsadmin`, данные — `goals-data.json`.
  Докручено в 1.4.20: пул шаблонов вырос с 8 до 24 (бой/охота, шахтёрство, ферма,
  магия/ремесло, мир/быт, общий котёл), активных целей за волну — 6 вместо 4.
  Фикс в 1.4.21: `description` с двоеточием без кавычек делал plugin.yml шести
  аддонов невалидным — они молча не грузились на сервере; добавлена CI-проверка.)*

## Приложение C. Порядок внедрения

**Волна 1 (сразу, P1):** п. 8 (хранение и миграции — база для остальных), п. 3 (сессия и 2FA),
п. 2 (антибрутфорс, часть — после п. 8), п. 5 (журнал и `pending` — деньги).
Перед этим — быстрые победы из Приложения A (пункты 1–3).

**Волна 2 (после стабилизации):** п. 1 (диалоги), п. 7 (предупреждения об истечении),
п. 9 (аудит + Discord), п. 4 (политика паролей).

**Волна 3:** п. 6 (тарифы и подарки), п. 11 (модерация чата), п. 12 (`messages.yml`),
п. 10 (статистика и диагностика).

**Волна 4 (архитектура):** крупные инициативы из Приложения B — в первую очередь MySQL/прокси,
если планируется больше одного сервера.

Каждый пункт стоит закрывать отдельным PR: правки затрагивают пересекающиеся классы
(`AccessManager`, `RegistrationStore`, `RegisterCommandHandler`), а изменения схемы `data.json`
(пп. 2, 4, 5, 8, 11) должны идти через версионирование из п. 8, иначе можно потерять данные игроков.
