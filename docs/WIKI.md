# Вики для игроков: источники, сверка и публикация

Сайт: <https://cherdakmd.github.io/CHRDK_F_REGISTER/>.
35 страниц в восьми разделах; сайт описывает версию **исходников**, а не состояние
запущенного Minecraft. Изменённые владельцем настройки могут отличаться.

## Сборка и проверки

```bash
python3 -m pip install -r tools/wiki/requirements.txt
python3 tools/wiki/build.py --check
python3 -m unittest discover -s tools/wiki -p 'test_*.py' -v
node --test tools/wiki/test_search.cjs
npm ci --prefix tools/wiki
(cd tools/wiki && npx playwright install --with-deps chromium)
npm test --prefix tools/wiki
python3 -m http.server 8000 --bind 0.0.0.0 --directory site
```

Результат — `site/`, не отслеживается Git. Без `--check` можно посмотреть черновик;
это **не** подтверждение смысловой актуальности. Проверенная публикация всегда
использует `--check`. Нужны Python 3.12+, Node 22 и Chromium для браузерных тестов.

## Что редактировать

- `wiki/<slug>.md` — объяснение для игрока, постоянный URL `<slug>.html`.
- `wiki/config.yml` — порядок разделов и страниц, подписи карточек, адрес сайта.
  Каждая страница должна встретиться ровно один раз.
- `tools/wiki/facts.py` — явный список публичных скаляров и генераторов таблиц.
- `tools/wiki/build.py` — небольшой Markdown-сборщик, HTML, локальные ссылки/якоря,
  sitemap, полный поисковый индекс, версия, дата и commit в `build-info.json`.
- `tools/wiki/assets/` — собственные CSS/JS, favicon и Minecraft-иллюстрации.
  Нет CDN и внешних шрифтов. Неиспользуемые старые иллюстрации сохранены как исходные ассеты.

Обязательные метаданные:

```markdown
---
title: "Территории и аренда"
description: "Чанки, роли и оплата участка."
review: [claims, core]
---
```

Поддерживаются заголовки, абзацы, списки, цитаты, простые таблицы, inline-code,
блоки кода и ссылки. Внутри ячейки экранируйте `\|`. Команды в inline-code,
начинающиеся с `/`, копируются по клику или Enter/Space. Параметры в угловых
скобках надо заменить перед выполнением. JavaScript не интерпретирует запросы
или текст индекса как HTML; результаты разрешены только на локальные страницы.

## Данные, которые не нужно переписывать руками

`{{fact:claim_price}}` подставляет выбранное публичное число.
`{{table:shop}}` — полный магазин; `{{table:enchants}}` — каталог из Java-реестра
с названиями из messages.yml; `{{table:commands}}` — классифицированные команды.
Есть таблицы рангов/товаров, лимитов, ежедневок, званий и состава модулей.
Неизвестное поле, новая неклассифицированная команда ядра, несовпадение схемы
или реестра — ошибка, а не пустая подпись.

Цены таблицы магазина — **базовые**, не итог сделки и не гарантированная выручка.
Команды администратора исключены; пересекающийся `/prof` у профиля не рекламируется
как стабильный алиас. Полные конфиги, delivery commands, API-токены и live-данные
не экспортируются. Новую таблицу добавлять только через явный whitelist полей.

## Когда меняется игровая механика

1. Обновить код, сообщения и тесты механики.
2. Выполнить `python3 tools/wiki/freshness.py`: он перечислит связанные страницы.
3. Прочитать изменённую реализацию/конфиги и заново проверить объяснения, команды,
   права, цены, ограничения и побочные эффекты. Даже если текст менять не нужно,
   сверка нужна: совпадение чисел не доказывает совпадение правил.
4. Исправить текст и явно принять **только сверенные** страницы:

   ```bash
   python3 tools/wiki/freshness.py --accept claims teleports \
     --reason "Сверены оплата аренды, роли, цена переноса и лимиты домов"
   ```

5. Добавить изменённый `wiki/reviewed.json` вместе с кодом и текстом, запустить
   полный набор проверок и отправить PR.

Команда принимает указанные страницы, но возвращает ошибку, если другие ещё
требуют сверки. Это ожидаемо. В CI нет `--accept` и автоматической перезаписи lock.
Новый модуль обязан иметь страницу с `review`. Отпечатки включают имена и содержимое
всех `.java`, `.yml`, `.json` в `src/main` связанных модулей и генератор фактов;
новый/удалённый файл тоже обнаруживается. Тестовые файлы и build-артефакты не учитываются.
Изменение генератора намеренно требует повторной сверки всех страниц.

Это консервативное **напоминание о ручной проверке**, не анализатор смысла и не
защита от намеренно неверного подтверждения. Оно не доказывает правильность
механик, всей прозы, финансового восстановления или установленной конфигурации.

## Как обновляется GitHub Pages

Канонический источник — `main`. Единый `.github/workflows/build.yml` срабатывает
на **каждый** push в `main` и `arena/**`, все PR и ручной запуск, без `paths`.
Параллельно выполняются:

- `build`: контракты/регрессии проекта и полный `./gradlew build` всех 25 плагинов;
- `wiki`: сверка исходников/текста, данные и ссылки, Python/Node-тесты, Playwright
  для desktop/mobile, проверки доступности основных страниц в обеих темах.

`deploy` имеет `needs: [build, wiki]` и допускается только из `main`, не из PR.
Ошибка любого этапа оставляет опубликованную версию неизменной. Независимого
`pages.yml` больше нет. Общая concurrency не отменяет начатый деплой.
Отдельный Release workflow также проверяет актуальность сайта перед сборкой ZIP.
Тег сам по себе не переключает Pages на код ветки: сначала нужна интеграция в `main`.

Порядок публикации: зелёный PR → merge → зелёные оба jobs на merge-коммите →
успешный `Deploy to GitHub Pages`. Сравнить commit можно в footer и
`build-info.json`; стили/скрипт получают hash-query, поиск — ревизию исходников.
Обновление Pages не устанавливает плагины, не изменяет сервер и не создаёт релиз.

## Проверяемое качество и границы

- Все страницы/ассеты/якоря, полнота навигации и отсутствие нераскрытых директив.
- Все 178 записей магазина доступны в HTML и поиске, а не только первые 1600 символов.
- Изменение кода/конфига/генератора/текста и добавление модуля требуют сверки.
- Все страницы без JS-ошибок и горизонтального сдвига на 390/1440 px;
  тёмная/светлая тема, поиск, ESC/фокус, копирование, отказ сети и no-JS.
- axe на главной, магазине и входе в обеих темах: автоматическая часть WCAG AA,
  не заявление о полной ручной сертификации доступности.

Игровой smoke-тест, доступность внешних ссылок и мониторинг сервера сюда не входят.
Открытые проблемы F03–F12 из общего аудита этим изменением не исправляются.
