# Дневные акции `/shop` — три способа заработать алмазы

> С 1.5.5 выплаты акций выражаются в сотых алмаза; настройки целых наград
> умножаются на 100 только при расчёте. Дневной лимит оборота удалён, а лимит
> самой акционной доплаты сохранён. Ниже — историческая архитектура 1.5.2.

Статус: **вошло в стабильный `1.5.2 KARAS UPDATE`** (тег `v1.5.2`,
`Latest=v1.5.2`, Release CI с тремя ассетами). `API_VERSION=42` без bump.
При реализации изменения лежали в ветке `arena/35241455-chrdk-f-register`
поверх `v1.5.2-rc.4`; полные заметки — [docs/releases/1.5.2.md](releases/1.5.2.md).

Запрос игроков: «нужно сделать ещё несколько способов заработка алмазов на
сервере, желательно дневные акции на различные товары в `/shop`». Решение
согласовано четырьмя развилками: `combo3` / `utc_rotation` / `bounded_ledger` /
`dev_only` (последняя снята владельцем при выпуске 1.5.2).

## 1. Что появилось

В алмазном магазине `CHRDK_DiamondShop` (не в донатном `/pass`) каждый
календарный день UTC действует **одна** из трёх акций. Тип и товары дня
выбираются детерминированно от номера суток — одинаково на всех серверах, без
случайности, без ручного назначения и без повторов внутри дня.

| Тип | Как заработать | Награда по умолчанию |
| --- | --- | --- |
| **Горячая скупка** | Продать любой из товаров дня | +25 % к выплате за сделку |
| **Заказ дня** | Сдать 64 единицы первого товара дня за сутки | 12 ⛁ разово |
| **Серия товаров** | Сдать 3 разных товара дня за сутки | 16 ⛁ разово |

Пул — 14 материалов из `items:` (`DIRT`, `COBBLESTONE`, `STONE`, `GRAVEL`,
`SAND`, `OAK_LOG`, `SPRUCE_LOG`, `WHEAT`, `COAL`, `REDSTONE`, `IRON_INGOT`,
`RAW_IRON`, `GOLD_INGOT`, `DIAMOND_ORE`), по 3 товара в день. Неизвестные и
недоступные для сдачи материалы отбрасываются при разборе конфига.

## 2. Границы дня и ротация

- `ShopPromoMath.dayIndex(now) = floorDiv(now, 86_400_000)` — **календарные
  сутки UTC**, то же окно, что и у персонального дневного оборота `ShopStore`.
  Сделано намеренно: акция и лимит оборота заканчиваются в один момент.
- `typeFor(day)` — цикл из трёх типов по `floorMod(day, 3)`.
- `featured(pool, count, day)` — сдвиг `day*7+3` по пулу и шаг, взаимно простой
  с размером пула: первые `count` позиций всегда различны. Один и тот же день
  даёт один и тот же набор, соседние дни — разные.
- Прогресс сбрасывается в `ShopPromoStore.rollDay()` при первом обращении в
  новые сутки; файл предыдущего дня не переносится.

## 3. Откуда берутся алмазы: `bounded_ledger`

**Бонус не эмитируется отдельным переводом.** Он входит в `money` и `credit`
той же самой сделки `ShopExchange`, поэтому проходит через WAL
(`ShopStore.prepare` → `ShopJournal.Pending` → `finish`), дневной оборот
`canRecordTurnover` и все прежние проверки. `ShopInventory.replay` для продажи
использует только `units`, а `ShopExchange.valid()` для продажи требует
`credit == money` — оба инварианта сохранены.

Потолки, применяемые в `ShopPromoMath.cap` (берётся минимум):

1. **Анти-арбитраж.** `бонус ≤ цена покупки того же объёма − базовая выплата`,
   то есть итоговая выплата за продажу никогда не превышает `ask × число партий`.
   «Купил в магазине → сразу продал дороже» остаётся невозможным; сохранены и
   прежние защиты `RecipeEconomy.cap` и `purchase-multiplier`.
2. `max-bonus-per-trade` = 32 ⛁ за сделку.
3. `max-bonus-per-player-per-day` = 128 ⛁ на игрока за сутки.
4. Свободное место в персональном дневном обороте: бонус включается в оборот и
   **не является обходом** `pricing.daily-cap.*`.

Если потолок равен нулю, акция честно ничего не добавляет: сделка проходит по
обычной цене, а не падает с ошибкой.

### Сделки с переносом остатка (`sellall`)

`ShopSaleRemainder` пересчитывает выплату из `salePrice`, поэтому для `carry`
бонус входит в **цену партии**: `perLot = бонус / число партий`, цена и остаток
пересчитываются заново, `validRemainder()` остаётся истинным. Фактически
начисленный бонус может быть чуть меньше запрошенного из-за целочисленного
деления; в прогресс записывается именно фактическая сумма.

## 4. Где лежит прогресс

Новый файл **`promotions-data.json`** в папке аддона:

```json
{"schema":1,"day":20000,"players":{"<uuid>":{
  "bonus":20,"contractPaid":true,"seriesPaid":false,
  "units":{"DIRT":64,"STONE":32}}}}
```

Важно: это **не новый root-ключ в `shop-data.json`** — строгий парсер рынка и
его whitelist не тронуты. Прогресс считает проданные единицы по материалам,
множество различных товаров, уже начисленный бонус и флаги разовых наград.
`record()` вызывается после успешного коммита **каждой** продажи, а не только
той, где выпал бонус: иначе условие заказа/серии никогда бы не набралось.

Файл пишется через временный файл и атомарный перенос. Повреждённый,
неизвестной схемы или частично битый JSON читается как пустое состояние с
предупреждением в лог: худший исход — акция не начислит бонус, но сделки и
деньги остаются корректными. При ошибке записи бонус уже внутри совершённой
сделки, деньги не откатываются; в лог пишется честное предупреждение.

## 5. Конфигурация

Секция `promotions:` в `diamond-shop/src/main/resources/config.yml`:
`enabled`, `pool`, `featured-per-day`, `hot-buyback-percent`,
`contract-units`, `contract-reward`, `series-kinds`, `series-reward`,
`max-bonus-per-trade`, `max-bonus-per-player-per-day`. Все числовые значения
зажимаются в безопасные диапазоны.

**Автообновление файлов владельца.** В `diamond-shop/src/main/resources/config-schema.yml`
поднята схема v2 → v3 (`config-version: 3`, `messages-version: 3`). При первом
запуске `ConfigUpgrader` аддитивно допишет в существующие `config.yml` и
`messages.yml` недостающие ключи вместе с комментариями эталона, создаст backup
(`config-before-schema-config-v3-*.yml` и `...-messages-v3-*.yml`), проставит
маркер и перечитает конфиг. Значения, комментарии и форматирование владельца
сохраняются; повторный старт файл не меняет, поэтому ключ, удалённый **после**
перехода на v3, уже не вернётся.

Переименований и удалений в v3 нет: шаги `migrations.*.remove` / `rename` не
объявлены, устаревших ключей изменение не вводило. Вывод товара из продажи
по-прежнему делается через `catalog.retired-materials`.

**Важное следствие перехода версии:** движок восстанавливает **все** отсутствующие
ключи эталона, а не только `promotions:`. Если администратор вручную удалял
товар из `items:`, он вернётся один раз при обновлении до v3. Для постоянного
исключения товара используйте `catalog.retired-materials`.

**Деградация.** Если секции в файле нет (владелец удалил её уже после v3, либо
файл собран вручную), `ShopPromoConfig.from` берёт стоковые значения, а
`Messages.load` подтягивает недостающие тексты из ресурса JAR: акции работают,
но изменить настройки можно только добавив блок `promotions:` вручную. Пул
дополнительно фильтруется по живому каталогу: пустой результат честно выключает
акции.

## 6. Что видит игрок

- В витрине `/shop` у товаров дня появляется строка «★ Товар дня».
- На кнопке баланса — тип акции, товары дня и остаток дневного бонуса.
- После продажи — отдельная строка «Акция дня: +N ⛁ к выплате за эту сделку».
- Никаких **новых команд, подкоманд, permission-нод, правок `plugin.yml`
  и изменений `API_VERSION`**: механика встроена в существующие `/shop` и GUI.

## 7. Проверки

| Тест | Что закрепляет |
| --- | --- |
| `ShopPromoMathTest` | сутки UTC, цикл из трёх типов, детерминированная ротация без повторов, все пять потолков `cap`, `askTotal`/`lots`/`percentOf` |
| `ShopPromoConfigTest` | аддитивный парсер, фильтрация пула по каталогу, клампы, `enabled: false`, пустой пул |
| `ShopPromoStoreTest` | переживает рестарт, сброс в новые сутки, битый/чужой JSON, нулевые и отрицательные бонусы |
| `ShopPromoServiceTest` | +25 % и запрет арбитража, суточный потолок на игрока, заказ разово на нужном объёме, серия из разных товаров, выключенные акции |
| `DiamondShopSchemaV3Test` | реальные `config.yml`/`messages.yml` аддона: переход v2 → v3 дописывает `promotions:` и три текста с комментариями, хранит владельческие значения и каталог (248 товаров), не добавляет корневой ключ в `messages.yml`, идемпотентен, удалённая после v3 секция не воскресает |
| `ConfigSchemaEngineTest.mixedIndentKeysAtSamePositionProduceReadableYaml` | вставки с разным отступом в одну позицию не ломают YAML |

**Попутное исправление движка.** Для v3 понадобилось починить
`ConfigSchemaEngine.addMissing`: три новых текста (`promo-bonus-paid` на 4
пробелах, `promo-line`/`promo-tag` на 6) попадали в одну точку вставки — конец
секции `trading`. При прежней сортировке внешний ключ шёл первым, более глубокие ключи
оказывались «после скаляра», YAML не читался и движок честно отказывался от
всей правки. Теперь вставки с одной позицией объединяются в один блок, внутри
которого сначала идут более глубокие отступы. Порядок при равных отступах
остался прежним (как в эталоне), поэтому остальные модули не меняют поведение.

Прежние контракты не ослаблены: `TradeResult` и `SellAllResult` получили поле
`bonus` с совместимыми конструкторами без него; старые конструкторы
`ShopService` передают `promos = null`, поэтому юнит-тесты, не знающие об
акциях, получают прежние выплаты.

## 8. Границы выпуска

При подготовке акций версию не bump'или, тег и релиз не создавали (`dev_only`);
при выпуске **1.5.2 KARAS UPDATE** это решение снято: `plugin_version=1.5.2`,
тег `v1.5.2`, стабильный Release CI с тремя ассетами и штатная новость ВК/MAX.
PR в `main` не открывался, поэтому канонический сайт GitHub Pages (деплой идёт
только из `main`) остаётся на прежней версии; исходники вики в теге — 1.5.2.

Не проверяли production, живой сервер, клиент Minecraft, RCON, TradeMC и игровой
smoke. Не меняли цены рангов, каталог `/pass`, 26 карточек TradeMC,
`API_VERSION`, `ShopStore` и формат `shop-data.json`. Не добавляли случайность,
ручное назначение акций и отдельную казну/эмиссию алмазов. Старые ключи
конфигов не удалялись; `migrations.*.remove` и переименований в схеме v3 нет.
