# Резервные копии CHRDK без MySQL

## Что защищено

`SafeJsonWriter` пишет временный файл рядом с состоянием, делает `fsync` данных,
атомарно заменяет основной файл и, где ФС позволяет, синхронизирует каталог.
Один писатель на путь исключает смешивание параллельных снимков. Основной
`data.json` аккаунтов использует тот же `fsync` и отдельный SHA-256.

Core создаёт ZIP-снимки в `plugins/CHRDK_Core/backups/snapshots/`. Включаются
файлы состояния `.json`, `.jsonl` и служебные `.yml` установленных папок
`CHRDK_*`. Конфиги, сообщения, API-токены, ключи, логи, аудит, кэши, старые
бэкапы и временные файлы исключаются. Файлы и каталоги-симлинки не читаются.

**Важно:** `data.json` содержит хэши паролей и секреты TOTP. ZIP приватный
(`0600` на POSIX), его нельзя публиковать или отправлять игрокам. Токены из
исключённых конфигов восстанавливаются из отдельного защищённого конфиг-бэкапа.

Перед снимком Core сбрасывает аккаунты, банк, надписи, звания и модерацию.
Каждый файл копируется целиком и проверяется. Между разными аддонами нет общей
транзакции/паузы записи: снимок согласован по каждому файлу, но не обещает
единый логический момент для всего сервера. При любой ошибке чтения, изменении
размера, невалидном JSON или записи архива частичный ZIP не публикуется.

Внутри ZIP: `CHRDK-BACKUP.json` и исходные относительные пути. Манифест содержит
формат, UTC-время, причину, размер и SHA-256 каждого файла. Готовый ZIP сразу
проверяется повторным чтением: CRC, точный состав, пути, лимиты, SHA-256 и JSON.

## Расписание и команды

`storage.snapshots` в `config.yml`: включение, снимок после запуска, интервал
(по умолчанию 60 минут), 6 последних + 14 ежедневных + 8 еженедельных копий.
Известные старые снимки удаляются только после успешной записи и проверки нового.
Файл с нестандартным именем автоматически не удаляется.

```text
/pass backup create                 # асинхронный ZIP + обязательная проверка
/pass backup list                   # ZIP и старые gzip аккаунтов
/pass backup verify <имя.chrdk.zip> # повторная независимая проверка
/pass backup legacy                 # прежний gzip только аккаунтов
/pass backup restore <legacy.gz>    # совместимость: только аккаунты Core
```

Полный ZIP намеренно нельзя восстановить внутри игры: работающие плагины иначе
могут снова перезаписать состояние и смешать версии WAL/квитанций.

## Проверка и восстановление

Нужны исходники репозитория и Python 3.11+, сторонних пакетов нет.

```bash
# Только проверка, ничего не распаковывает на диск:
python3 tools/backup/restore_chrdk_backup.py chrdk-YYYYMMDD-HHMMSS-manual.chrdk.zip

# СНАЧАЛА полностью остановить сервер. Не /reload, не PlugMan.
python3 tools/backup/restore_chrdk_backup.py chrdk-....chrdk.zip \
  --restore --plugins-dir /srv/minecraft/plugins --confirm SERVER_STOPPED
```

Скрипт повторно проверяет манифест, CRC, хэши, JSON, Zip Slip и симлинки. Старые
версии заменяемых файлов сохраняются в `CHRDK_Core/backups/pre-restore/`, новые
готовятся во временном каталоге и заменяются через `os.replace`. После этого
нужно сверить установленный комплект JAR и только затем запускать сервер.
Откат конфигов выполняется отдельно — их в ZIP намеренно нет.

Контрольный restore без остановки production делается в пустом staging:

```bash
mkdir -p /tmp/chrdk-restore-test/plugins
python3 tools/backup/restore_chrdk_backup.py /path/to/snapshot.chrdk.zip \
  --restore --plugins-dir /tmp/chrdk-restore-test/plugins --confirm SERVER_STOPPED
```

Здесь `SERVER_STOPPED` подтверждает, что цель не является работающим production;
не указывайте production-каталог для такого теста.

## Парная целостность Claims и Core

Финансовая операция Claims записывается в два журнала: `CHRDK_Claims/claims-data.json`
хранит локальный lineage, sequence и pending-WAL, а `CHRDK_Core/bank.json` —
зарегистрированный lineage, банковский баланс и durable receipt/high-water. Снимок,
созданный на работающем сервере, согласован по отдельным файлам, но **не гарантирует
один общий момент** между этими двумя плагинами. Поэтому одного ZIP, снятого при
работающем сервере, недостаточно как гарантированно согласованной точки отката.

Для чистого запуска или восстановления:

1. Как дополнительную точку сохранения можно сделать `/pass backup create` и дождаться
   успешной независимой проверки ZIP. Не считайте этот онлайн-снимок атомарным между
   Claims и Core.
2. Штатно остановить весь сервер и дождаться завершения процесса. После остановки
   скопировать одним комплектом миры, playerdata, конфигурации, точные JAR и все
   `plugins/CHRDK_*`, обязательно вместе с `claims-data.json`, `bank.json` и их WAL.
   Не собирать эту пару из разных дат/архивов.
3. Если нужен rollback, восстанавливать обе стороны из одной офлайн-копии при
   остановленном staging; не подменять только `claims-data.json` или только `bank.json`.
4. После запуска staging выполнить только read-only `/claimadmin recovery` до любых
   финансовых действий. Допускать обычный тест только если `ready=true`, `pending=false`,
   local/Core lineage совпадают и local/Core sequence равны.
5. При любом mismatch, unavailable или unknown outcome не удалять и не редактировать
   файлы, не повторять оплату и не пробовать отдельные восстановления. Сохранить обе
   исходные копии и полный startup log, остановить staging и разбирать точную причину.

Эти проверки не доказывают причину прежнего production-отказа; для этого нужны
реальные логи и копии состояния инцидента. Принимать новый lineage автоматически
допустимо только для подтверждённо пустой финансовой истории без pending; иначе
операции должны остаться закрытыми до согласованного восстановления.

## Внешняя копия и регламент

Локальная ротация не защищает от отказа диска/VM. Минимум раз в сутки копировать
`snapshots/` на другой хост или в объектное хранилище, с шифрованием и ограничением
доступа. Пример после успешного автоматического снимка:

```bash
rsync -a --chmod=Fu=rw,Fgo=,Du=rwx,Dgo= \
  /srv/minecraft/plugins/CHRDK_Core/backups/snapshots/ backup-host:/private/chrdk/snapshots/
```

Рекомендуемый регламент: ежедневная проверка свежести и свободного места,
еженедельный `verify` внешней копии, ежемесячный контрольный restore в staging.
Сохраняйте вывод внешней системы копирования; серверный лог не подтверждает,
что архив действительно оказался на другом устройстве. Секретный внешний
credentials-файл не кладите в `plugins/CHRDK_*`.

Перед обновлением можно дополнительно сделать `/pass backup create`, дождаться
успешной проверки и скопировать ZIP вне сервера. Но для согласованной точки отката
обязательно выполните штатную остановку и сохраните офлайн-копию всего комплекта,
включая миры, playerdata, конфигурации, LuckPerms, сторонние плагины и точный набор
JAR. Онлайн-снимок не заменяет эту копию. MySQL не требуется и сам по себе ни одну из
этих операций не заменяет.
